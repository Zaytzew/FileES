Chapter 2: User Guide

2.1 Client Installation

VerifiedLinux user bundle accepted; Windows daemon and GUI activate, join a realm and sync live. The MSI still packages the GUI only.

Linux (bundle from build-gui.sh)

# Unpack the filees-client-linux-amd64 bundle
chmod +x install-user.sh
./install-user.sh                     # installs to ~/.local/
ENABLE_AUTOSTART=1 ./install-user.sh  # install + enable autostart

The installer copies the daemon binary to ~/.local/bin/filees, the GUI binary to ~/.local/bin/filees-gui, the mobile-pairing helper to ~/.local/bin/filees-pair-gui (spawned by the tray as needed — see §2.6 — never launched directly by the user), an icon, and a .desktop file. It installs a systemd --user unit (filees.service) but does not enable an inactive service without explicit request; an already active service is restarted by default (set RESTART_DAEMON=0 to suppress that restart). An existing config.json is never overwritten on upgrade.

To start the daemon as a user service:

systemctl --user enable --now filees.service

Windows GUI artifact (MSI)

Run build-msi.ps1 in PowerShell on a machine with the WiX Toolset wix command (verified with WiX v7), then install the generated .msi. A first WiX v7 build needs the one-time command wix eula accept wix7. Installation is per-user; no UAC prompt is required. The Start Menu shortcut has System.AppUserModel.ID = ATMProjekt.FileES, enabling toast notifications. The current MSI still installs only the GUI. The Windows daemon is built and run as a separate filees.exe; it is not yet packaged as a Windows service or scheduled task. Live activation, realm join, selective attach and cross-client sync have been accepted against a production OpenBSD server.

Before uninstalling the MSI on Windows: run filees-gui --autostart disable first. The installer does not automatically remove the HKCU\...\Run registry value that the application creates.

2.2 Configuration

VerifiedValidation and non-overlapping working-copy roots are enforced before runtime state creation.

Everyday shape of the installation is changed in Settings (§2.6), not by editing a file. The daemon still reads config.json from the working directory (or --config). An existing file is never overwritten on upgrade. Working-copy paths must be absolute and must not nest. The field table is in Operations.

To validate configuration without starting the daemon:

filees config-check --config /path/to/config.json

2.3 First Run and Onboarding

Verified on OpenBSD and WindowsNew-realm activation and administrator-authorised join of another desktop installation are owned by the daemon and GUI.

Someone with keys on the server sends you an e-mail invitation — see invite. On this desk choose Activate client on a new server…, paste the invitation from the first letter, then paste the OTP from the second. You never type a server address, port or client identifier. The GUI only presents the steps; the daemon owns the network and the files.

A normal invitation opens a new realm (strefa). The window asks that empty realm once for an immutable alias. An invitation bound to an existing realm inherits that alias and its folders; you are not asked to rename it. Optional folders stay unattached until you connect them in Settings.

If activation already reached accepted and then stopped, choose Resume. A different invitation may replace only unfinished state. An existing client-profile.json is a hard stop.

Adding a local directory

In Settings choose the server, then Połącz z lokalnym folderem (or add a new folder you own). FileES checks that the server has room, creates the share, and publishes the first snapshot. If there is not enough room you see the required and available sizes. A failure is shown in the window; it is not left silent. The three durable tickets behind that action are in Operations.

2.4 Day-to-Day Sync

VerifiedNormal operation, outage accumulation, bounded shutdown and restart reconciliation tested.

Once active, the daemon operates without user interaction:

  • Local file changes are detected within one watch_interval tick. New files wait 5 minutes before their first commit.
  • Commits are grouped by the tier matching the current staged size (commit_tiers).
  • Server changes are pulled every poll_interval. If a conflict is detected the local copy is preserved in !kolizje/ and the server version wins.
  • The daemon recovers from network outages automatically with backoff. Staged changes accumulate in cache.json and are published when the connection is restored.
  • On controlled shutdown (SIGINT/SIGTERM) the daemon drains the staging in bounded batches within shutdown_commit_timeout. Any remaining changes are written to cache.json and resumed on next start.

File ignore patterns

Built-in ignores (cannot be overridden): ~\$* (MS Office), .~lock.*# (LibreOffice/OpenOffice), *.tmp, *.bak, .DS_Store, Thumbs.db, desktop.ini, .vscode/, .idea/, *.swp, *.swo, node_modules/, __pycache__/, *.o, *.pyc, .git/.

User-defined ignores: place patterns in .filees/user_ignore.cfg (hot-reloaded on every scan). Lines starting with ! are hard ignores that skip entire subtrees. Glob syntax supports ** for any depth.

2.5 Edit Passports

Verified cross-clientRepository-wide policy, owner-only control, projection and two-client lock transfer passed live acceptance on Windows.

Edit passports are an optional, repository-wide lock. The owner turns them on once under Zasady edycji in FileES Settings. The column Edycja then shows wymaga wypożyczenia. Guests cannot change the policy. The default is ordinary free editing. Why it is opt-in, and the timing numbers, are in Operations.

Behaviour under passport mode:

  • All existing regular files are migrated to carry svn:needs-lock on first start (the daemon refuses to start migration if the working copy has local content changes, deletes, or missing files).
  • A file without an active passport is locally read-only. For a repository whose owner realm is not this client's own realm, it becomes writable only after a successful repo.lock / filees lock call, including the Lock files… action in the repository tray submenu.
  • Autolock (owner realm): for a repository this client's own realm owns, no manual lock action is needed at all. Right after every svn up, the daemon makes its own read-only files locally writable immediately — before the real SVN lock is acquired. The real lock is only requested at the moment of the next commit attempt for that path: if the repository is genuinely free (or the lock is already held by another of this same realm's own instances, which is taken over silently, no dialog), the commit proceeds; if a different realm already holds the lock, the commit is held back and the change stays staged for a later retry — it is never stolen, and the local edit is never lost.
  • New files do not need a passport before their first publication.
  • After a confirmed send the file stays writable for a short grace, then returns to read-only.
  • A competing desk sees who holds the file and when that hold ends. A stale row in the window cannot release a different hold.

Changing the policy is a migration, not a local preference. Files held by someone else are left alone and retried later. A guest with read-write access still uses Wypożycz do edycji; autolock is only for the owner realm. Per-path ownership and Poproś o zwolnienie are not in this version.

2.6 GUI Tray

VerifiedGUI is a separate binary over contract/v1; Windows join, selective attach, working-copy recovery and journal were accepted on a live installation.

filees-gui is a separate process. It only talks to the daemon. Closing the tray does not stop synchronisation. Why that split exists is in Operations and GUI boundary.

In progress: a new Wails-based desktop client (a full WebView window instead of a tray-plus-native-dialogs surface) will eventually replace the Fyne + zenity/yad tray described here. It is still under development and unreleased — the description below remains what you actually install and run today.

Journal

The tray contains one combined Dziennik rather than separate activity and error menus. It orders both sources newest-first, aggregates paths from the same repository revision or stage, and merges a failed activity with the structured error carrying the same error ID. At most 12 rows are rendered in the system tray. Otwórz log… opens the complete available snapshot in a native window; Windows renders error rows in bold dark red. The tray API cannot style individual native menu rows, so it uses an explicit ⚠ BŁĄD prefix and an error count in the Journal title.

FileES Settings window

The tray menu is for day-to-day work: state, opening a directory, locking and unlocking files, and the global reservation list. Anything that changes the shape of the installation lives under the FileES menu as Ustawienia…, so administration is not opened once per server and long directory names never have to compete with actions inside a GNOME submenu.

The sequence is fixed: pick the server, pick the action, then see the share list only when that action is about a working copy. Realm visibility, the send/fetch wait, adding a folder, deactivation and removing the share do not require selecting a share first. Repositories granted to the realm still appear in the folder step even when they are not present on this device. Destructive scope, retention and the full warning text are shown there rather than in a menu label.

After choosing Połącz z lokalnym folderem, Windows allows selecting several unattached shares; Linux shows the same filtered list. Once repo.attach_approve succeeds, Settings overlays the chosen path and łączenie…, disables duplicate connection and keeps polling the durable lifecycle until the daemon's authoritative snapshot reports Attached or a terminal error.

Repository and installation lifecycle

Six different actions are deliberately kept distinct. The wording matters because connecting, recovering a moved working copy, local detach and destructive server removal have different effects:

ActionSubjectServer effectLocal effect
ConnectOne repository already present in this realm's projectionNo grant change; authenticated SVN access is used for the first checkout.Creates a durable attachment and checks out into the selected local directory.
Locate working copyAn attached repository whose root is missingNoneValidates an existing .svn root, exact repository URL and FileES identity marker, then rebinds local_path without checkout and without discarding local changes.
Detach folderOne working copyNoneStops FileES for that directory and removes .svn and .filees. Your files stay exactly where they are.
Detach permanentlyOne repository you ownRemoves the live FSFS repository and its authorisation. With positive retention the server first writes a verified SVN dump with a SHA-256 manifest.As above.
Deactivate this client…One installationRevokes this installation's key. Grants and repositories of the realm are untouched.Detaches this installation's working copies, removes its profile and key.
Remove FileES share…The whole realm on that serverWithdraws every grant of the realm, deletes the realm's own repositories and revokes all of its installations. Gated by a mailed OTP.Detaches the current installation and removes its profile.

The last one runs a fixed sequence and cannot be shortened: a warning with the derived scope, an explicit consent step, the notification address for the OTP, a directory chosen by you for the .fkr recovery kit, and only then the OTP prompt. The kit is written before the operation reaches its irreversible boundary, because after the removal completes there is no client credential left with which to obtain one. Keep it — without it the archives cannot be fetched (§4.8). Permanent detach of a single repository likewise requires two separate confirmations.

Permanent removal is always limited to repositories of your own realm. It can never reach a share belonging to another realm, nor a repository with attachment_policy=required. Detaching a folder never deletes user files — that applies to every row above.

Realm alias: the GUI asks once only for a new, empty realm's immutable globally unique alias. Another installation joining an existing realm inherits the canonical alias in its first projection and is never invited to rename it. If repositories are already projected but the alias is empty, this is incomplete server projection data, not an alias-creation task. Visibility and lock actions remain unavailable with an explicit projection message until reconciliation; a matching idempotent claim can repair an older server view.

Realm grants and visibility

The GUI shows the realm concept to end users under the plain-language label strefa (§2.10). Where this manual says "realm" below, the desktop window says "strefa".

Two further actions appear in the same FileES Settings window (Linux: yad radiolist; Windows: PowerShell DataGridView) once the daemon reports the corresponding capability:

  • Widoczność… (realm_visibility, IPC realm.set_visibility) toggles this realm's own entry in the private recipient directory between hidden and listed. A realm must be listed before another realm can pick it as a grant recipient; toggling visibility never reveals repositories or existing access — only whether this realm can be found at all.
  • Uprawnienia gości (manage_grants, IPC realm.grant_recipients + repo.grant_access / repo.revoke_access), reachable per repository row, lists visible realms plus hidden realms that still hold an active grant. The current access column shows none, read-only or read-write, so hiding a recipient realm never makes its existing grant unmanageable. Every change asks for confirmation and immediately regenerates data-authz and every affected installation's view.json in the same worker operation.

Public shares from the desktop

Udostępnienia publiczne is on the owner’s repository row. How to create a channel, what the recipient sees, and why it is not a live mirror of the folder are in the Shares chapter.

Reconnect behaviour

If the daemon is unreachable, the GUI retries with exponential backoff: 1 s → 2 s → 5 s → 10 s → 30 s. The last known snapshot remains visible but is marked stale. “Reconnect” in the menu forces an immediate retry.

Lock and unlock appear only while the daemon is reachable and advertises them. The hello / subscribe / resync sequence is in Operations.

Server activations

Each active server is listed by its user-chosen alias and groups its repositories underneath. The technical host is not used as the primary label. Server information… shows the address, SSH port, client ID and effective client role. A transport configuration without an activation does not create a synthetic default server. If at least one activation exists, the tray header says Client activated.

Folder lifecycle

For each attached, optional working copy the server menu exposes Detach folder “name”… before the expandable folder row, so the action remains reachable even when the folder submenu is long. It stops FileES for that directory and removes only .svn and .filees; your files stay as an ordinary folder. Connecting again is a first checkout into a new or empty directory — it does not merge the preserved folder by itself. Detach permanently needs two confirmations and removes the live server repository. With positive retention the server keeps a verified dump until retain_until.

The folder FileES is watching is an identity, not just a path. If it vanished, Settings shows Wskaż kopię — pick the existing copy; do not create an empty replacement. FileES will not invent a healthy empty folder in its place.

Restore from archive

Odtwórz z archiwum… (load_dump, IPC repo.load_dump, ticket LOAD_REPOSITORY_DUMP) is reachable from the FileES Settings window for a selected repository row, alongside Detach and Detach permanently. It loads a previously exported SVN dump as a fresh generation of that repository, through the same staged, verified, atomic-swap mechanism filees-rotate uses internally (§4.7) — the worker locates the uploaded dump itself; the client never sends a filesystem path or revision range. The first release ships without an options dialog: filtering always applies the server's current ignore policy, and the full source history is kept (see LOAD_REPOSITORY_DUMP_CONCEPT.md for the scope-limiting parameters the ticket contract already supports).

File reservations

The header item File reservation list… opens one native Linux/Windows window for every live SVN lock observed through this installation's locally attached working copies, across active servers. It is enabled only when at least one reservation exists. Each row names the server, working copy, repository-relative path, owner realm alias and local creation time (HH:MM DD-MM-YYYY). Rows are ordered by working copy and then path; the window can refresh without closing. It is deliberately not a server-administration inventory: a repository with no local working copy cannot be observed through this client.

Choosing Release always asks for confirmation. Release all asks once and releases only the reservations this client is entitled to release; every release is separately token-fenced. Local modifications or an active edit passport add an explicit warning about unsaved editor data. FileES does not use “is the file open?” as a safety gate because many editors save by atomic replacement and such a check would be misleading. A foreign or other-device reservation shows the placeholder Request release (coming soon) and cannot be released here. The dialog returns only opaque row IDs; the daemon re-lists each lock and matches its token before releasing, so a stale row cannot release a different lock.

Activate client on a new server… consumes the opaque invitation issued by the server administrator; the invitation already contains the canonical server address, port and pinned host key. After the daemon begins onboarding, the GUI displays Enter the OTP code…. Before importing another invitation the daemon reports accepted local attempts without an active client profile. The GUI offers Resume: it first tries the durable reconnect identity, and if that identity was not authorised before the interruption it requests the OTP for the same stored attempt. This includes accepted passports written by older clients. A different server-signed invitation may supersede incomplete ephemeral state, but an existing client-profile.json is a hard boundary and cannot be overwritten by onboarding. On success the daemon emits activation.changed and triggers a full snapshot refresh. A new empty realm is then asked for its immutable alias. A ticket bound with --join-realm-alias produces an existing-realm projection instead: the GUI opens the normal server-management path where repositories can be selectively connected, and it does not ask the user to claim a different alias. Reconnecting the GUI manually is not part of the successful flow.

Pairing a mobile device

Once a server is activated, its tray submenu offers Pair mobile device… — visible whenever the connection is Connected and not Stale, regardless of the client's role or repository-creation permission (pairing a phone is not gated the same way repository creation is). The action calls mobile_pairing.begin, which mints a short-lived (5 minute) MOBILE_PAIRING token through the daemon's own already-authenticated control-plane channel, then hands the token, server address and pinned host key to a separate helper process (filees-pair-gui) over its standard input — the daemon itself never renders anything.

filees-pair-gui is deliberately a distinct binary and process, not part of filees-gui: it opens a small local web page (bound only to 127.0.0.1, on an OS-assigned port, at a random per-session path) in the system's default browser. The page asks for a local PIN before it will display anything; on first use it offers to set one. Entering the correct PIN renders the pairing QR code, which the FileES mobile app scans to complete pairing — after which the phone inherits, once, the same repository list the pairing desktop currently has. The helper closes itself automatically once the QR code has been shown for a short grace period, once the token expires, or after a period of inactivity — whichever comes first. What the phone does after pairing is in the Android client page.

The local PIN is stored encrypted at rest. The primary wrapping key is bound to a random device_id written next to pin.json, not to a network MAC address — docking, a new NIC or interface reordering no longer permanently lock the user out. Records encrypted with the older MAC-derived key still decrypt; the first successful verify re-wraps them onto the device key. A copy of the PIN file taken to a different computer or account cannot be decrypted. A wrong PIN is rejected with a limited number of attempts; once exhausted, the PIN must be set again (there is currently no separate recovery/reset flow). The same PIN can optionally be required every time filees-gui itself starts, as a local screen-lock — off by default, and unrelated to any server-side authentication. On Windows both files are protected by a per-user DACL, not by a POSIX mode bit.

Autostart

filees-gui --autostart enable    # write autostart entry for current executable path
filees-gui --autostart disable   # remove entry
filees-gui --autostart status    # enabled / enabled-stale / disabled

enabled-stale means the entry points to a different path or arguments than the current executable. Re-run --autostart enable from the installed location to fix it. On Linux this writes an XDG .desktop file to ~/.config/autostart/; on Windows it writes to HKCU\Software\Microsoft\Windows\CurrentVersion\Run.

2.7 Signed Desktop Updates

Verified end to endSigned SVN release, dry run, existing Linux installer, anti-rollback and controlled GUI restart are covered by a reproducible integration test.

Desktop updates are opt-in. The build carries one trusted public key; Settings cannot replace it or skip the signature. The envelope and anti-rollback rules are in Operations.

User flow

  1. A verified newer release adds a New update available badge to the tray menu.
  2. Show what will change… performs a fresh signed dry run. On Linux it compares the daemon, GUI and icon, reports regenerated desktop/service entries and explicitly marks an existing configuration as unchanged.
  3. Update and restart… resolves and verifies the release again, then shows a native confirmation dialog with the plan.
  4. On approval the existing platform installer runs from the verified bundle. Linux disables installer-internal autostart and daemon restart and preserves the user's configuration.
  5. After successful apply and durable high-water update, the GUI shuts down its loops, releases the single-instance lock and only then launches the newly installed executable with the original arguments.
Do not bypass the updater. A locally restored older binary does not lower the high-water mark. Emergency binary recovery and authorising a remote downgrade are separate operations; publishing an older sequence under the normal channel is rejected.

Release operators must use the offline signing workflow in tools/RELEASE_PUBLISHING.md. Private release keys must never enter the source repository, build host, client bundle or test VM.

2.8 CLI Commands

ImplementedCommands use daemon IPC and do not bypass the engine with direct SVN mutation.

All CLI sub-commands communicate with the running daemon through the Unix socket and never invoke svn directly:

filees status               # state of all repositories
filees lock   <file>...    # acquire SVN lock
filees unlock <file>...    # release SVN lock
filees log [N]              # last N error log entries (default 20)
filees config-check         # validate config without starting daemon
filees help

One command deliberately does not use the daemon, because it has to work on a machine that has no FileES installation left:

filees recovery download --kit FILE.fkr --output DIR

It reads a recovery kit produced during removal of a FileES share and fetches that operation's archives over the _filees-recovery account, verifying the pinned host key, the archive identity, its size and its SHA-256 against the manifest carried in the kit. See §4.8.

lock and unlock accept multiple files and group them by repository automatically. Relative paths are resolved to absolute and validated as lying inside a working copy.

Daemon log level (environment variable):

FILEES_LOG=debug ./filees
FILEES_LOG=trace ./filees   # includes svn invocations
# Available: silent error warn info (default) debug trace

2.10 GUI Terminology (Glossary)

ImplementedTracks every case where the desktop GUI's Polish vocabulary deliberately diverges from the architecture's SVN-derived terminology.

The desktop GUI is Polish-only and targets non-technical end users. Where the architecturally correct term — used throughout this manual, the codebase and the wire protocol — would expose SVN- or protocol-level jargon with no intuitive meaning to a user, the GUI substitutes plain language instead. Internal identifiers, IPC field names and protocol messages keep the architecture term unchanged; only what the user reads changes. The mapping is 1:1 and stable: a given GUI term always corresponds to exactly one architecture term.

GUI term (Polish)Architecture termMeaning
strefarealmThe durable identity of an owner (a person or organisational unit) that can span multiple installations/devices, owns repositories, and is the subject grants and shares bind to. See Identity and grant model.

Add a row here whenever another GUI-facing term is deliberately renamed for the same reason, in the same commit that changes the strings.
