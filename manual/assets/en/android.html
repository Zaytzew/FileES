Android client

The phone is a capture and preview device, not an editing station. It reads a share like a public listing. It writes only under mobile-uploads/. The rest of the tree stays read-only. Protocol detail lives in Tech filees-mobile-v1 and in concepts/TREE_INGEST_CONCEPT.md.

What it is

Live-tested2026-08-16 on spot: QR pairing, share listing, download, a 198-file folder in one commit, tree visible on the desktop.

The app never creates repositories and never asks for a UUID. After pairing it shows the same shares the desktop has in the realm projection. Opening a share is a folder-and-file list with human sizes. The launcher mark is f:s; folder rows use the square filees:space symbol.

Pairing

On an already activated desktop: tray → server → Pair mobile device…. A local page asks for a PIN and shows a QR code (five minutes). The phone scans it. After a successful pair the home scan button goes away; emergency pairing stays under Settings (the gear).

The phone inherits that desktop's share list. It does not create a realm. How the desktop issues the QR is in the desktop guide.

Browse and download

The back arrow walks up the tree (the bar sits below the status bar, not under it). A file has Download and lands in the system Downloads collection. A file downloaded and edited on the phone does not write back to the original path — if you send it, it goes to mobile-uploads/ as a new object.

Send

Add offers files or a whole folder. The destination is always mobile-uploads/… in the chosen share. A small set goes one by one, with a 3 / 7 spinner. An existing path under mobile-uploads/ with the same content is skipped; different content is a new revision, with no conflict prompt.

Large folder

From eight files up, the phone first totals their count and size (198 files, 14 MB), packs the folder into one zip (transport packaging only, not a file in the share) and sends it in one connection. The server worker checks the header sha256, unpacks the contents, and makes one commit. If the file you send is itself a .zip archive that is your document, it is stored as a regular file — the server does not unpack it a second time.

This reduces the overhead of sending many small files at once; it does not change how a single very large file is handled. Long-session time limits are a separate desktop concern.

Tracked folders

Live-verified2026-08-29: fixed a real bug where background sending silently did nothing unless a repository happened to be open in the share browser.

In Settings you pick a folder on the phone and a send destination (repository/share). The app checks the folder roughly every five minutes and sends new files automatically — the send destination is now independent of whichever repository you happen to be browsing. When you turn on tracking for a folder that already has content, the app asks whether to send all of it or only files added from now on. Every successful background send ends with a system notification.

What the phone does not do

  • it does not edit or delete objects outside mobile-uploads/;
  • it does not create shares and does not take a typed UUID;
  • it does not show an upload queue — a spinner, then success or an error.

The server must support UPLOAD_TREE (the signed release with this feature; on spot from r543). An older filees-mobile-v1 exits status 70. In that case the phone reports that the server does not support the operation or is not yet accepting bulk uploads — the app does not report a false success.
