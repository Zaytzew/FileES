FILEES-SERVING-STATE(8) System Manager's Manual FILEES-SERVING-STATE(8)

NAME

filees-serving-state — answer one FileES reservation and server-state query

SYNOPSIS

filees-serving-state [-config path] client-id

DESCRIPTION

filees-serving-state is the one-shot worker behind the filees reservation-v1 forced command. filees-client-entry(8) authenticates the key, unveils what the worker needs and executes filees-serving-state with the client ID of that key. An operator does not run it.

It reads one bounded JSON request from standard input and writes one JSON result to standard output. Legacy reservation requests are limited to 4 KiB; batch and public-link state requests are limited to 1 MiB. The request schema selects the answer:

filees.reservation/v1
The Subversion locks of one repository, as reported by svn(1).
filees.reservation/v2
The same for one repository, together with whether that repository is still active, or the server ID and display name when no repository is named.
filees.reservation/v3
Per-object lock ownership of one repository for automatic locking, refreshed under the service working copy lock.
filees.reservation-batch/v1
A scope-bound, paginated emission for the authenticated client's view. The initial request obtains state; subsequent requests may name known content versions and receive unchanged acknowledgements or changed results. Each page covers at most four repositories and is checked as one observation.
filees.public-links-state/v1
An authenticated management snapshot or differences for owned public links, including removals. It grants no public-recipient access or new sharing authority.

A client may ask only about repositories that are active in its own server-issued view. Any other request fails without an answer. A filees.reservation/v2 request about a repository withdrawn from the client's realm is answered as deleted and the repository is not queried.

The last known lock state is kept under reservation-projection in the repository results root. When a live query fails, the result carries the last stored answer marked stale, or is marked unknown when there is none.

Acknowledgements require current source checks. On Unix the lock source is the local SVN lock index; revision authors and canonical authority records remain independently checked. Direct administrative changes may leave HEAD unchanged. History reuse binds the physical repository incarnation as well as UUID and revision.

FileES writer markers and a durable observation epoch reject responses intersected by a mutation, including between repositories in a batch. An interrupted marker is not silently removed and does not permit a cache-only acknowledgement. Failed, incomplete or unsupported observations are not empty inventories and do not refresh client authority lifetimes.

Clients fence in-flight reads across their own mutations. A canonical acknowledgement updates only the affected path or link; saved presentation state never proves freshness by itself.

The worker keeps its own pledge(2) promises narrower than its parent's and does not call unveil(2) itself; the table is inherited from filees-client-entry(8).

The installed image is root: wheel mode 0555 in /usr/local/libexec/filees.

FILES

/etc/filees/server.json
Default configuration; -config names another absolute path.

EXIT STATUS

sysexits(3) values as in filees-admin(8).
