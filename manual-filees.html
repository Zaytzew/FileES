Chapter 1: Mechanics and Architecture

1.1 Protocol Overview

VerifiedCurrent architectural contract and tested client/server foundations.
Manual rule: significant architectural choices are recorded with their rejected alternatives and cost. This is part of the specification, not historical commentary.

FileES is a file-synchronisation daemon that keeps local working directories in sync with a remote SVN repository. SVN is used here purely as a transport and storage layer — revision-control semantics are secondary. The target user experience is a silent tray icon that keeps files synchronised without the user ever needing to know that SVN is involved.

The system is designed around the following principles:

  • Convergence, not journalling. The periodic scanner captures end-state between ticks. Several filesystem operations between two scans may collapse into a single SVN commit.
  • No data loss. The commit staging map is written atomically to disk after every event. If the daemon dies between a commit being accepted by the server and the working-copy metadata being updated, the next restart reconciles by querying SVN status and skipping already-accepted entries.
  • HEAD wins. Conflicts are resolved by keeping the server version. The local conflicting version is preserved in a timestamped !kolizje/ directory before svn resolve --accept theirs-full is called.
  • Push deploy. Client identity (an Ed25519 key pair) is provisioned by the server through a reverse SSH tunnel initiated by the client. The server never holds a private key.
Design rationale / convergence instead of event journalling
Decision
The periodic scanner records the observable end-state at scan boundaries.
Why
FileES synchronises content convergence; it does not need to reproduce every user gesture or filesystem syscall.
Rejected
Using inotify/fsnotify as the source of truth; maintaining a durable operation journal.
Cost
Several operations between scans may collapse into one commit or a no-op.

For each configured repository the daemon runs an independent pipeline:

Scanner (pkg/watcher)

Periodically walks the working-copy tree and compares current state with the manifest stored in .filees/state/manifest.json. Change detection uses mtime, size, and MD5 hash. Files under 64 MiB are hashed inline within a per-scan budget; larger files are queued in a persistent MD5 backlog processed one-at-a-time by a background worker that always picks the smallest pending file. This enables rename detection even for large files.

Deletion events are debounced for 5 minutes (equal to the new-file latency) so that a file that is deleted and immediately re-created does not produce a spurious delete commit. During an active commit (commit.busy flag) the scanner switches to lightweight mode, watching only .filees/tickets/.

Design rationale / periodic scanner instead of OS event dependence
Decision
The manifest and persistent MD5 backlog are authoritative for change detection.
Why
A missed kernel event, daemon downtime or platform-specific watcher behaviour cannot permanently hide a change.
Rejected
Treating native filesystem notification streams as a complete and durable history.
Cost
Detection latency is bounded by watch_interval, and scanning consumes predictable I/O.

Commit Service (pkg/commit)

Coalesces scanner events per path and, on each commit tick, produces batches bounded by max_batch_files (default 100) and max_batch_mib (default 512 MiB). A single file larger than the MiB limit gets its own batch so it cannot starve the queue. If total staged bytes reach backlog_flush_mib (default 1024 MiB) and at least one entry is outside the new-file latency window, a flush is forced without waiting for the regular interval.

Before any SVN operation, each path is re-classified by svn status --xml --verbose to confirm its actual state in the working copy. Empty commits are prohibited.

Design rationale / planner plans; committer publishes
Decision
Batch selection and publication remain separate responsibilities even when both grow under chaos testing.
Why
Planning owns ordering, size and starvation rules. Publication owns SVN effects, confirmation and reconciliation.
Rejected
Splitting by line count; allowing the publisher to invent batching policy; extracting fragments without a finished contract.
Cost
The planner and committer may remain large because failure handling deepens their responsibility without widening it.

HEAD Poller and Reconciliation

Every poll_interval (default 30 s) the daemon fetches the server HEAD revision. If HEAD exceeds the local revision, svn update is called. Before any update, a full recursive status is run; a missing entry defers the update so that local deletes and rename sources are not reconstructed from the server. Conflicts found after update are handled by copying the local version to !kolizje/<timestamp>_lokalne/ with a .meta sidecar, then calling svn resolve --accept theirs-full and emitting a RECON-3002 error.

Design rationale / HEAD wins without silent local loss
Decision
The server version resolves the working-copy conflict, but the local version is copied to !kolizje/ first.
Why
The daemon must converge without interactive blocking, while preserving every conflicting local payload for later review.
Rejected
Interactive merge dialogs in the daemon; silently discarding either side; leaving the working copy indefinitely conflicted.
Cost
Users may need to review conflict copies manually, and the archive can accumulate.

IPC Server (pkg/ipcserver) and Client (pkg/ipcclient)

The daemon exposes a Unix domain socket at \$XDG_RUNTIME_DIR/filees.sock (fallback: ~/.filees/daemon.sock). The protocol is filees.contract/v1 — versioned JSON Lines, one object per line. Normal requests are request/response; events.subscribe switches the connection to a server-push stream. Currently implemented commands include system.hello, system.status, system.restart, system.shutdown, signed-update commands, activation and mobile pairing, repository lifecycle commands (repo.create_request, repo.attach_intent, repo.attach_approve, repo.relocate, repo.locate, repo.load_dump, detach and delete, repo.lifecycle_status), realm-grant commands (repo.grant_access, repo.revoke_access, realm.alias_claim, realm.grant_recipients, realm.set_visibility, realm.remove_begin, realm.remove_confirm), repo.activity, repo.lock, repo.unlock, repo.reservation_list, repo.reservation_release, error.list and events.subscribe. Commands are advertised individually as capabilities; a client must not infer availability from this list. repo.pause, repo.sync_now, repo.publish, conflict decisions and notices remain declared in the contract but unwired.

Design rationale / events invalidate snapshots
Decision
GUI events are signals to refetch daemon-owned snapshots, not a second state machine.
Why
A lost event, reconnect or version gap cannot make the GUI permanently diverge from daemon truth.
Rejected
Building durable GUI state solely by replaying an event stream; letting the GUI inspect .filees or execute SVN.
Cost
The GUI performs additional status reads after events and remains intentionally dependent on the daemon contract.

Runtime Gates (pkg/runtime)

HostGate limits the number of concurrent commits across all daemon instances on the host (directory-based locking). RepoMutex enforces at most one commit at a time per repository. Both use atomic directory operations with PID, creation timestamp, and a unique owner token. On Linux/POSIX (S3 correction), the owner file carries an OS-managed flock so that PID recycling cannot produce a false “lock is still held” result.

1.4 Bundle Layout and Filesystem Protocol

VerifiedAtomic claim/commit and recovery paths tested natively on OpenBSD.

The server side uses a filesystem-based protocol with no hidden database or background daemon. A single committed filees.onboarding-bundle/v4 JSON file is the atomic record of an onboarding operation. It contains three sub-objects: Operation, Outbox (delivery state retained, OTP and address redacted after terminal delivery), and Audit (append-only history). One rename(2) publishes all three atomically.

Design rationale / filesystem protocol instead of hidden transactional service
Decision
One versioned bundle and atomic rename publish operation, outbox and audit together.
Why
The exact crash point remains visible and can be inspected or completed with ordinary system tools.
Rejected
A private database as the only source of workflow truth; resident FileES server daemons; opaque recovery journals.
Cost
Cross-resource effects still require idempotent steps and reconciliation; filesystem durability requires explicit fsync.

1.5 OTP Mechanism

VerifiedOTP storage, attempt limits, redaction and BSD Auth handoff implemented.

The one-time password for tunnel authorisation has 120 bits of entropy encoded as Base32 in the format LLLLLLLL-SSSSSSSSSSSSSSSS. The 40-bit prefix is a locator that identifies the operation bundle without exposing the operation ID. The full value is verified as HMAC-SHA-256 against a server-side private pepper (minimum 256 bits) stored at the path given by otp_pepper_file in server.json.

Each wrong attempt atomically decrements a counter stored in the bundle. On expiry, OTP exhaustion, or successful use the hash and locator are erased from the bundle. The plaintext OTP exists only in the pending mail outbox entry until the mail is accepted by the smarthost (250 after DATA), at which point the delivery address and OTP are atomically redacted.

Why

Rejected

Cost

The push deploy and activation flow:

  1. Entry A — onboarding request. The client SSH-connects with a compiled bootstrap Ed25519 key to _filees-onboard. The bounded filees-bootstrap-entry reads one versioned filees.onboard-request/v1 frame, runs the atomic onboarding take, and then performs exactly one SMTP outbox submission. Connection then closes; no FileES mail daemon remains running.
  2. Entry B — OTP and reverse tunnel. After receiving the OTP by email, the client runs:
    ssh -F /dev/null -l _filees-tunnel -T \
  -R 127.0.0.1:42000:127.0.0.1:<local-helper-port> \
  <server> "filees tunnel-v1"
    The OTP is supplied through a FIFO-based askpass (SSH_ASKPASS_REQUIRE=force). BSD Auth validates the OTP by reading the login_-filees style and atomically advances the bundle to tunnel_authorized. filees-entry confirms the SSH_ORIGINAL_COMMAND is exactly filees tunnel-v1, claims the tunnel grant (advancing to tunnel_started), then execs filees-worker deploy.
  3. Worker — identity generation. filees-worker connects through the reverse tunnel to the client-side helper using a pinned Ed25519 worker key. The helper accepts only filees-deploy/v1. For generate_identity, the client generates an Ed25519 key pair locally; only the public key and fingerprint cross back to the worker. The private key never leaves the client machine.
  4. Access staging and possession proof. The worker stages a restricted line in /var/filees/activation/authorized_keys and read-only SVN authz. It then asks the same helper to perform prove_service_access. The client opens a new SSH connection as _filees-client with the installation private key and the fixed command svnserve -t. After system sshd authenticates the key, filees-client-entry writes a server-side receipt and execs the configured svnserve. A helper response alone is never accepted as proof.
  5. Activation publication. After validating the receipt, the worker commits the service format, realm, client record, first client view and audit event in one SVN revision, then advances the operation to active. The active key retains read-only access only to its own client subtree.

The client-side helper is a minimal SSH server listening only on loopback with an ephemeral host key. It refuses shell, PTY, subsystems, global requests, and any command other than filees-deploy/v1. Responses are size-limited to 64 KiB using io.LimitReader before decoding (S3 hardening).

Authenticated control plane

Once a client is active it reaches the server over the same _filees-client account with SSH_ORIGINAL_COMMAND set to filees control-v1. filees-client-entry then runs filees-worker repository-control <client_id> and relays one versioned ticket frame. The worker serialises every control request behind a single file lock, so requests from different sessions never interleave.

Identity and authority always come from the forced-command session, never from the ticket body: the worker resolves client_id from the per-key command binding and the realm from the server-side projection. The ticket family currently accepted is:

1.7 pledge / unveil Sandbox Model

Verified on OpenBSDPer-command pledge/unveil profiles and dispatcher/worker exec boundary tested natively.

On OpenBSD every server-side tool calls pledge(2) and unveil(2) with per-command minimal profiles. The process flow is:

parse argv / verb
  -> pledge("stdio rpath wpath unveil")   # bootstrap
  -> load and canonicalise config
  -> read-only preflight of private layout  (before unveil lock)
  -> unveil(exact paths, exact perms)
  -> unveil(NULL, NULL)                   # lock
  -> pledge(runtime promises)             # reduce
  -> open prepared repo handle and execute
Design rationale / one command, one sandbox profile
Decision
Each short-lived tool and verb receives only its exact paths and syscall promises.
Why
A compromise or programming error should remain bounded by the function the process was launched to perform.
Rejected
A broad shared daemon profile; configurable promise strings; granting capabilities for hypothetical future work.
Cost
Profiles require native tests and may reveal runtime-specific minimums such as loader access or startup setrlimit.

Key invariant: pledge and unveil profiles are closed in code. Only the dispatcher, activation worker, client entry and administrative revoke retain the narrowly required proc exec boundary for a fixed executable; no promise or executable path is supplied by a network request.

Two exec disciplines

An unveil(2) table survives execve and, once locked with unveil(NULL, NULL), can never be replaced or extended — not even by a child that wants a narrower one. A dispatcher must therefore pick one of two disciplines up front, and the choice determines what its children may be:

DisciplineCallConsequence for the child
Pre-unveiled childobsandbox.ApplyForExecThe parent builds and locks the table; the child must not call unveil itself and instead opens prepared handles (onboarding.OpenPrepared). Used by filees-client-entry → filees-worker.
Self-sandboxing childobsandbox.PledgeForExecThe parent restricts promises only and leaves the table open, so the child can install and lock its own narrower profile. Used by filees-bootstrap-entry → filees-onboard, filees-mail.

Mixing the two — exec'ing a self-sandboxing tool from a dispatcher that already locked its table — fails at the child's first unveil call with EPERM, and does so only on OpenBSD, since the sandbox is a no-op elsewhere. Any new server-side child process has to be classified against this table before it is wired in.

The filees-entry binary is setuid to _filees-state. filees-worker is mode 0555 and inherits the effective UID through exec. This split is required because OpenBSD refuses to execute a setuid/setgid image when execpromises are set.

1.8 Service Repository

Activation and grant control plane implementedClient activation projection, read-only ACL and the canonical realm-grant store are implemented and covered by Linux/OpenBSD E2E (§4.4 of EXECUTION_ORDER.md / reports/REALM_GRANTS_E2E_2026-08-01.md).

The service repository (also called the technical repository) is a private SVN repository that acts as the versioned control plane. It does not store synchronised user files. Each monitored directory has its own separate data repository.

Design rationale / SVN service repository as versioned control plane
Decision
Canonical non-secret records and all affected client projections are committed in one SVN revision.
Why
The system gains atomic publication, history, inspectable files and deterministic projection rebuilds without a separate database service.
Rejected
SQL/Redis as domain truth; client-writable inboxes; storing full control-plane state only in generated authz files.
Cost
Effects outside SVN form durable sagas and need a reconciler; clients receive projections rather than arbitrary queries.

The implemented activation vertical stores the following non-secret persistent state:

  • Realms and their immutable identifiers
  • Client instances, client_id, public keys, fingerprints
  • Repository ownership and canonical realm-to-repository grants
  • Per-client read-only views
  • Activation and revocation audit events
  • Service format version

Implemented directory layout:

/
├── format.json
├── admin/
│   ├── realms/<realm_id>.json
│   ├── clients/<client_id>.json
│   ├── repositories/<repo_id>.json
│   ├── grants/<repo_id>/<recipient_realm_id>.json
│   └── audit/<operation_id>.json or <operation_id>-revoke.json
└── clients/
    └── <client_id>/

The activation manager and authenticated repository worker are the bounded writers in this vertical. Each active client has read-only SVN access to its own /clients/<client_id>/ subtree and no visibility into admin/ or other clients. One SVN commit publishes the client record, realm if new, projection and audit event atomically. A client joining an existing realm inherits that realm's immutable alias in its first view. Repository ownership (admin/repositories/) and canonical realm-to-repository grants (admin/grants/, see §5.5) are implemented; each grant/revoke and visibility change regenerates the affected clients' view.json and server-side authz in the same worker operation. Grant rebuild also reconciles the canonical realm alias, and an idempotent matching alias claim repairs older views that omitted it. A broader admin console beyond filees-admin (§4.1) remains a separate, later concept (signed-ticket V3, VERTICALS.md priority 8).

2.3 First Run and Onboarding

Verified on OpenBSD and WindowsNew-realm activation and administrator-authorised join of another desktop installation are owned by the daemon and GUI.

The onboarding flow provisions one installation identity and activates its first service-repository projection. It starts with an administrator-issued e-mail invitation. On the client, choose Activate client on a new server…, paste the one-time invitation from the first e-mail, then paste the separately delivered OTP when prompted. The invitation carries the server profile and its pinned SSH host key, so a normal user never types a server address, port, profile name, client UUID or known_hosts path. A normal ticket authorises a new realm and the GUI asks that new, still-empty realm once for an immutable alias. A ticket created with --join-realm-alias instead binds the invitation to an existing realm before delivery: the client cannot choose or submit that realm ID, inherits its alias and grants, and must not be asked to rename it. The GUI only presents the flow; the daemon owns all network and state transitions.

  1. Administrator creates a ticket as _filees-state: filees-admin ticket create you@example.com for a new realm, or adds --join-realm-alias existing-alias for another installation of an existing realm. The default configuration is /etc/filees/server.json; the default TTL is 24 hours.
  2. The server sends the first e-mail invitation through its configured relay. The invitation is an opaque single-use capability plus a pinned public server profile.
  3. Redeeming the invitation creates the short-lived operation and causes the server to send the OTP in a second e-mail. The server does not expose an address- or alias-availability probe. The daemon supplies the OTP through FIFO askpass and establishes the assigned reverse tunnel to its loopback helper.
  4. The helper generates an Ed25519 installation key locally. The worker stages access, asks the helper for service proof, and validates the receipt written after system-sshd authentication.
  5. The worker publishes the client record and first view in the service repository and marks the operation active. A joined client's first view contains the canonical existing realm_alias and all effective repositories, but optional repositories remain locally unattached until the user selects them.
Acceptance status: revoke followed by a fresh GUI activation, real SMTP delivery, OTP entry, reverse tunnel, installation-key proof and external svn info passed on the persistent OpenBSD 7.9 reference VM. A second Windows installation also joined an existing realm through a server-bound ticket and completed selective repository checkout. Release engineering still has to provide production pins, release-bound bootstrap-key rotation and a signed-payload policy. See reports/WINDOWS_REALM_JOIN_WC_AND_JOURNAL_FIX_BLOCK_2026-08-10.md.

Adding a local directory

The local provisioning state machine drives the following data-repository process against the authenticated server-side repository worker (pkg/repoworker), which is connected and verified end to end — including its refusal path:

  1. STORAGE_PREFLIGHT — the client sends an authenticated ticket with the local snapshot's total size; the worker checks it against the physical filesystem's available capacity (optionally through a reservation ledger that accounts for other in-flight operations) and refuses with STORAGE_INSUFFICIENT (exact required/available bytes, rendered in human-readable units) if there isn't room.
  2. CREATE_REPOSITORY — the client sends an authenticated ticket to the server worker, which creates the SVN data repository, sets the owner grant and ACL, and returns a canonical repo_id and repo_url.
  3. INITIAL_COMMIT — the client checks out the empty repository root into the local directory, performs a controlled svn add respecting ignore patterns, publishes the initial snapshot in bounded batches, confirms INITIAL_COMMIT, and only then starts the normal sync pipeline.

The local state machine preserves operation_id across retry, and each ticket type is idempotent on the worker side (a repeated request with the same operation_id replays the durable result rather than re-executing). After successful repository creation the client records the returned repository identity durably before starting its import, so a restart or retry resumes that import instead of creating a duplicate server repository. A failure at any of these three durable boundaries is reported back to the GUI via repo.lifecycle_status polling rather than left silent.

2.4 Day-to-Day Sync

VerifiedNormal operation, outage accumulation, bounded shutdown and restart reconciliation tested.

Once active, the daemon operates without user interaction:

  • Local file changes are detected within one watch_interval tick. New files wait 5 minutes before their first commit.
  • Commits are grouped by the tier matching the current staged size (commit_tiers).
  • Server changes are pulled every poll_interval. If a conflict is detected the local copy is preserved in !kolizje/ and the server version wins.
  • The daemon recovers from network outages automatically with backoff. Staged changes accumulate in cache.json and are published when the connection is restored.
  • On controlled shutdown (SIGINT/SIGTERM) the daemon drains the staging in bounded batches within shutdown_commit_timeout. Any remaining changes are written to cache.json and resumed on next start.

File ignore patterns

Built-in ignores (cannot be overridden): ~\$* (MS Office), .~lock.*# (LibreOffice/OpenOffice), *.tmp, *.bak, .DS_Store, Thumbs.db, desktop.ini, .vscode/, .idea/, *.swp, *.swo, node_modules/, __pycache__/, *.o, *.pyc, .git/.

User-defined ignores: place patterns in .filees/user_ignore.cfg (hot-reloaded on every scan). Lines starting with ! are hard ignores that skip entire subtrees. Glob syntax supports ** for any depth.

2.5 Edit Passports

Verified cross-clientRepository-wide policy, owner-only control, projection and two-client lock transfer passed live acceptance on Windows.

Edit passports provide explicit per-file locking with heartbeat renewal. The mode is selected once for the whole repository: its owner chooses Zasady edycji in FileES Settings, the server stores the canonical editing_policy, and every desktop projection receives the same value. The GUI column Edycja shows wymaga wypożyczenia to owners and guests; only the owner can change it. The default is ordinary free editing. On the wire the default is omitted and the only explicit value is lock_required.

Design rationale / repository policy remains opt-in
Decision
Explicit per-file locking is enabled only where the document type and workflow justify the friction.
Why
Ordinary synchronization should remain silent; pessimistic locking is a policy, not a universal property of FileES.
Rejected
Requiring locks for every repository; configuring a repository-wide barrier independently on each client.
Cost
Passport repositories require migration, read-only enforcement, heartbeat and server-visible token fencing.

Behaviour under passport mode:

  • All existing regular files are migrated to carry svn:needs-lock on first start (the daemon refuses to start migration if the working copy has local content changes, deletes, or missing files).
  • A file without an active passport is locally read-only. For a repository whose owner realm is not this client's own realm, it becomes writable only after a successful repo.lock / filees lock call, including the Lock files… action in the repository tray submenu.
  • Autolock (owner realm): for a repository this client's own realm owns, no manual lock action is needed at all. Right after every svn up, the daemon makes its own read-only files locally writable immediately — before the real SVN lock is acquired. The real lock is only requested at the moment of the next commit attempt for that path: if the repository is genuinely free (or the lock is already held by another of this same realm's own instances, which is taken over silently, no dialog), the commit proceeds; if a different realm already holds the lock, the commit is held back and the change stays staged for a later retry — it is never stolen, and the local edit is never lost.
  • New files do not require a passport before their first publication; the daemon assigns svn:needs-lock before the commit.
  • Commits use svn commit --no-unlock so that SVN does not bypass the close-grace period.
  • After a confirmed commit, the daemon waits for the close-grace period (edit_passport_close_grace, default 5 m) before unlocking and returning the file to read-only.
  • The server-visible SVN lock and its token are authoritative between clients. A competing client receives the holder alias and expiry; release and takeover re-read and fence the token so a stale UI row cannot release a different lock.

Changing the policy is a migration, not a local preference. Enabling it applies and commits svn:needs-lock to existing regular versioned files. Disabling it removes that property and releases passports owned by the caller. Paths currently held by another owner are left untouched and retried later rather than stolen. The mobile append-only projection intentionally does not receive editing_policy.

Scope of autolock (V1): a repository's owner realm is whichever realm created it (OwnerRealmID) — the same realm identity described in §5.5. Cross-realm repository sharing is implemented (§5.5): an owner can grant another realm r or rw access to a repository. Autolock itself remains strictly scoped to the owner realm (pkg/commit only runs the silent acquire/relock path when RealmID == OwnerRealmID); a realm holding only a granted rw share uses the manual "Wypożycz do edycji" path (§2.6) like any other non-owner user. Generalizing autolock priority to per-path ownership for repositories writable by multiple realms remains a separate, not-yet-implemented extension (concepts/AUTOLOCK_CREATOR_OWNERSHIP_CONCEPT_V2.md).

Realm alias: the GUI asks once only for a new, empty realm's immutable globally unique alias. If repositories are already projected but the alias is empty, this is incomplete server projection data, not an alias-creation task. Visibility and lock actions remain unavailable with an explicit projection message until reconciliation; a matching idempotent claim can repair an older server view.

Realm grants and visibility

The GUI shows the realm concept to end users under the plain-language label strefa (§2.10). Where this manual says "realm" below, the desktop window says "strefa".

Two further actions appear in the same FileES Settings window (Linux: yad radiolist; Windows: PowerShell DataGridView) once the daemon reports the corresponding capability:

  • Widoczność… (realm_visibility, IPC realm.set_visibility) toggles this realm's own entry in the private recipient directory between hidden and listed. A realm must be listed before another realm can pick it as a grant recipient; toggling visibility never reveals repositories or existing access — only whether this realm can be found at all.
  • Uprawnienia gości (manage_grants, IPC realm.grant_recipients + repo.grant_access / repo.revoke_access), reachable per repository row, lists visible realms plus hidden realms that still hold an active grant. The current access column shows none, read-only or read-write, so hiding a recipient realm never makes its existing grant unmanageable. Every change asks for confirmation and immediately regenerates data-authz and every affected installation's view.json in the same worker operation.

Public Shares from the desktop

Udostępnienia publiczne appears on a repository row only for the canonical owner and only when the daemon advertises the complete list/create/update/revoke/delete capability set. Its native Windows or Linux window shows each active or revoked channel with the public address, source root, recipients, password-protection flag and HEAD/frozen revision. The owner can create, edit, revoke or delete a channel; revoke stops delivery but retains the channel record, while delete retains the address tombstone.

Create and edit require an attached local working copy. The owner may select the working-copy root or any directory below it. The GUI recursively maps up to 4096 regular files, always skips .svn and .filees, rejects symlinks and preserves an existing object's stable public_id when its repository path remains present. An empty directory is a valid placeholder with an empty explicit map; files added later are not published automatically, so the owner must edit the channel to rebuild its map. A recipient list creates a closed per-recipient-token channel. An empty list creates an open channel that may carry a shared password. Password plaintext is converted to an Argon2id verifier before the control-plane ticket is constructed and is never stored in SVN-backed control state. During edit the server may preserve its existing verifier without returning it through control or IPC. An empty revision follows HEAD; a positive revision sets do-not-follow.

The canonical public address is https://<server-domain>/<realm-alias>/<slug>. The server's system HTTP listener routes that virtual address to the credential-free FileES link service; no matching filesystem directory or separate central short-link service is required. The landing page exchanges access policy for a short-lived signed visit, lists only the explicit object map and serves full files or byte ranges from an authoritative SVN revision. Revoking the channel invalidates both the main address and already issued visit/file links immediately, including files already present in the public cache.

Reconnect behaviour

If the daemon is unreachable, the GUI retries with exponential backoff: 1 s → 2 s → 5 s → 10 s → 30 s. The last known snapshot remains visible but is marked stale. “Reconnect” in the menu forces an immediate retry.

Initialisation sequence

  1. Send system.hello, store capabilities.
  2. Send events.subscribe (if capability present) before fetching snapshots.
  3. Fetch system.status, repo.list, and repo.status for each repository.
  4. On reconnect, sequence gap, or unknown event: perform full resync.

Events are cache-invalidation signals. The GUI never builds state purely by applying events; each event triggers a fresh repo.status fetch. Mutation actions (lock/unlock) are shown only when the daemon reports them as capabilities and the connection state is Connected (not Stale).

Server activations

Each active server is listed by its user-chosen alias and groups its repositories underneath. The technical host is not used as the primary label. Server information… shows the address, SSH port, client ID and effective client role. A transport configuration without an activation does not create a synthetic default server. If at least one activation exists, the tray header says Client activated.

Folder lifecycle

For each attached, optional working copy the server menu exposes Detach folder “name”… before the expandable folder row, so the action remains reachable even when the folder submenu is long. It stops FileES handling for that directory and removes only .svn and .filees; user files remain as an ordinary local directory. The final durability boundary uses platform-aware directory sync: real fsync on POSIX and the documented no-op on Windows, where flushing a directory handle returns ERROR_ACCESS_DENIED. Reconnecting later performs a first checkout into a new or empty directory; it never merges the preserved ordinary folder implicitly. A rejected target or lifecycle conflict is shown in an owned modal error window as well as a notification. If the active realm owns the repository and has repository-administration capability, the same server menu additionally exposes Detach permanently “name”…. It requires two confirmations, removes the active server repository and generated access projection, then detaches the local directory. With positive server retention, the worker stores a verified SVN dump and SHA-256 manifest until retain_until; it is not an immediate unrecoverable erase.

The working-copy root is tracked identity, not merely a convenient path. Before starting either an RW or RO pipeline, the daemon requires local .svn, verifies the exact projected repository URL with svn info, and validates or safely migrates .filees/state/working-copy.json. A missing or substituted root becomes interaction_required / working_copy_missing; FileES does not recreate the directory, initialise .filees there, or advertise a false healthy revision zero. Settings then exposes Wskaż kopię, which sends repo.locate to adopt a validated existing working copy without checkout. On Windows an active pipeline also retains a directory handle without delete sharing, so an external root rename/delete is blocked until a controlled FileES quiesce releases it.

Restore from archive

Odtwórz z archiwum… (load_dump, IPC repo.load_dump, ticket LOAD_REPOSITORY_DUMP) is reachable from the FileES Settings window for a selected repository row, alongside Detach and Detach permanently. It loads a previously exported SVN dump as a fresh generation of that repository, through the same staged, verified, atomic-swap mechanism filees-rotate uses internally (§4.7) — the worker locates the uploaded dump itself; the client never sends a filesystem path or revision range. The first release ships without an options dialog: filtering always applies the server's current ignore policy, and the full source history is kept (see LOAD_REPOSITORY_DUMP_CONCEPT.md for the scope-limiting parameters the ticket contract already supports).

File reservations

The header item File reservation list… opens one native Linux/Windows window for every live SVN lock observed through this installation's locally attached working copies, across active servers. It is enabled only when at least one reservation exists. Each row names the server, working copy, repository-relative path, owner realm alias and local creation time (HH:MM DD-MM-YYYY). Rows are ordered by working copy and then path; the window can refresh without closing. It is deliberately not a server-administration inventory: a repository with no local working copy cannot be observed through this client.

Choosing Release always asks for confirmation. Release all asks once and releases only the reservations this client is entitled to release; every release is separately token-fenced. Local modifications or an active edit passport add an explicit warning about unsaved editor data. FileES does not use “is the file open?” as a safety gate because many editors save by atomic replacement and such a check would be misleading. A foreign or other-device reservation shows the placeholder Request release (coming soon) and cannot be released here. The dialog returns only opaque row IDs; the daemon re-lists each lock and matches its token before releasing, so a stale row cannot release a different lock.

Activate client on a new server… consumes the opaque invitation issued by the server administrator; the invitation already contains the canonical server address, port and pinned host key. After the daemon begins onboarding, the GUI displays Enter the OTP code…. On success the daemon emits activation.changed and triggers a full snapshot refresh. A new empty realm is then asked for its immutable alias. A ticket bound with --join-realm-alias produces an existing-realm projection instead: the GUI opens the normal server-management path where repositories can be selectively connected, and it does not ask the user to claim a different alias. Reconnecting the GUI manually is not part of the successful flow.

Pairing a mobile device

Once a server is activated, its tray submenu offers Pair mobile device… — visible whenever the connection is Connected and not Stale, regardless of the client's role or repository-creation permission (pairing a phone is not gated the same way repository creation is). The action calls mobile_pairing.begin, which mints a short-lived (5 minute) MOBILE_PAIRING token through the daemon's own already-authenticated control-plane channel, then hands the token, server address and pinned host key to a separate helper process (filees-pair-gui) over its standard input — the daemon itself never renders anything.

filees-pair-gui is deliberately a distinct binary and process, not part of filees-gui: it opens a small local web page (bound only to 127.0.0.1, on an OS-assigned port, at a random per-session path) in the system's default browser. The page asks for a local PIN before it will display anything; on first use it offers to set one. Entering the correct PIN renders the pairing QR code, which the FileES mobile app scans to complete pairing — after which the phone inherits, once, the same repository list the pairing desktop currently has. The helper closes itself automatically once the QR code has been shown for a short grace period, once the token expires, or after a period of inactivity — whichever comes first.

The local PIN is stored encrypted at rest with a key derived from this machine's own hostname, account and MAC address (never written to disk) — a copy of the PIN file taken to a different computer or account cannot be decrypted. A wrong PIN is rejected with a limited number of attempts; once exhausted, the PIN must be set again (there is currently no separate recovery/reset flow). The same PIN can optionally be required every time filees-gui itself starts, as a local screen-lock — off by default, and unrelated to any server-side authentication.

Autostart

filees-gui --autostart status    # enabled / enabled-stale / disabled

enabled-stale means the entry points to a different path or arguments than the current executable. Re-run --autostart enable from the installed location to fix it. 2.7 Signed Desktop Updates

Verified end to endSigned SVN release, dry run, existing Linux installer, anti-rollback and controlled GUI restart are covered by a reproducible integration test.

Desktop updates are opt-in and fail closed. A production client build embeds only the trusted OpenBSD signify public key and its canonical key_id; the configuration cannot replace that key or disable signature verification. The daemon advertises update.status, update.plan and update.apply only when the complete signed update service has been registered.

The signed release envelope v2 binds the release ID, monotonic sequence, security_epoch, expiry time, component and platform to a separately signed artifact manifest. The client verifies the signify format internally with standard Ed25519, then checks the bundle's exact size and SHA-256 before extraction. Its private, fsynced high-water state rejects sequence rollback, security-epoch rollback and a different release reusing the same sequence.

User flow

  1. A verified newer release adds a New update available badge to the tray menu.
  2. Show what will change… performs a fresh signed dry run. On Linux it compares the daemon, GUI and icon, reports regenerated desktop/service entries and explicitly marks an existing configuration as unchanged.
  3. Update and restart… resolves and verifies the release again, then shows a native confirmation dialog with the plan.
  4. On approval the existing platform installer runs from the verified bundle. Linux disables installer-internal autostart and daemon restart and preserves the user's configuration.
  5. After successful apply and durable high-water update, the GUI shuts down its loops, releases the single-instance lock and only then launches the newly installed executable with the original arguments.
Do not bypass the updater. A locally restored older binary does not lower the high-water mark. Emergency binary recovery and authorising a remote downgrade are separate operations; publishing an older sequence under the normal channel is rejected.

Release operators must use the offline signing workflow in tools/RELEASE_PUBLISHING.md. Private release keys must never enter the source repository, build host, client bundle or test VM.

3.2 Running install-server.sh

Verified on OpenBSDGeneric and OpenBSD integration paths include the complete activation vertical.

The generic installer script is packaging/server/install-server.sh (also included in the bundle at dist/filees-server-openbsd-amd64/).

# As root or with doas:
./install-server.sh

What the installer does:

  • Installs filees-admin and filees-operation to \$PREFIX/sbin/ (default /usr/local/sbin).
  • Installs filees-onboard, filees-bootstrap-entry, filees-mail, filees-entry, filees-worker, and filees-client-entry to \$PREFIX/libexec/filees/.
  • Creates /etc/filees/ (mode 0700) and copies server.example.json to /etc/filees/server.json if not already present.
  • Generates a 256-bit random OTP pepper: /etc/filees/otp.pepper (mode 0600).
  • Generates an Ed25519 worker key pair: /etc/filees/worker_ed25519 (mode 0600) and /etc/filees/worker_ed25519.pub (mode 0644).
  • Creates the private state directory: /var/filees/onboarding/{tickets,operations,audit}/ (mode 0700).
  • Creates the private activation skeleton at /var/filees/activation/; the OpenBSD integration step assigns final ownership and initialises the service repository.
The generic installer deliberately does not create an rc.d or systemd service and does not touch sshd_config. The sshd integration is the separate OpenBSD step below.
OpenBSD upgrades must preserve set-id entry modes. On an already integrated host, running only install-server.sh is not a complete upgrade: the generic script writes ordinary 0755 files and can replace ownership/modes assigned by install-ssh.sh. Run both stages and validate sshd -t, or atomically replace only a specific ordinary binary with its documented owner and mode. The short-lived filees-worker is root:wheel 0555 and has no resident service to restart; bootstrap, tunnel, client, mobile and recovery entries have distinct set-id modes and must never be overwritten generically without restoring them.

OpenBSD sshd integration: install-ssh.sh

# As root, after the generic install:
./packaging/server/openbsd/install-ssh.sh

What install-ssh.sh does:

  • Creates _filees-state and the three protocol accounts _filees-onboard, _filees-tunnel, and _filees-client. Protocol accounts use /bin/sh only to permit sshd forced commands; interactive shell, PTY and user RC remain disabled by sshd policy.
  • Installs the login_-filees BSD Authentication style binary to /usr/libexec/auth/.
  • Installs the filees-tunnel login class and rebuilds the database with cap_mkdb.
  • Writes a validated Match User fragment to /etc/ssh/sshd_config.d/filees.conf (creating the sshd_config.d/ directory and updating the main sshd_config Include if needed).
  • Installs the bootstrap authorized key for _filees-onboard to /etc/ssh/filees_bootstrap_authorized_keys.
  • Installs the set-id dispatchers, creates /var/filees/activation, initialises /var/filees/service-repo and its working copy, and connects svnserve to the generated authz file.
  • Verifies the configuration with sshd -t and reloads the existing sshd.

Regenerating the OTP pepper invalidates all outstanding OTPs. Any client in the middle of an onboarding will need a new ticket. Regenerating the worker key pair requires updating the pinned public key on all clients before the next deploy attempt.

3.6 Managed Install and Upgrade: filees-install

Implemented, channel not provisionedThe manifest-driven updater core exists, but no production FILESS-BIN repository, signed channel or release key has yet been provisioned.

filees-install is the implemented manifest-driven successor to the server shell installers, modelled on the ksefUCK upgrade channel. Its intended distribution repository (FILESS-BIN) has not yet been created, so the commands below describe the target workflow rather than the current production deployment path. The binary is present in the build bundle but the current generic install-server.sh does not install it. Until the signed channel, production signify key and complete ownership policy are delivered, server upgrades use a reviewed bundle copied to the host, followed by both install-server.sh and openbsd/install-ssh.sh; running only the first stage is unsafe on an integrated OpenBSD host.

# Plan against the configured channel (no changes):
filees-install -check
# Full plan including config-contract drift, no payload download:
filees-install -dry-run
# Install or upgrade to the channel head (or a named release):
filees-install -apply [r7]
# Stage-1 rollback: restore the previously installed files:
filees-install -rollback
# Stage-2 rollback: remove files, sshd fragment, login class and
# the users this installer created; keeps /var/filees and /etc/filees:
filees-install -purge
# ... and wipe operational state too (irreversible):
filees-install -purge -wipe-state

Configuration lives in /etc/filees/install.conf (INI: [repo], [local], [install], [policy], [security]). Key behaviours:

  • First install also performs the system tasks that install-ssh.sh covers today: creates the protocol accounts (recording which ones it actually created), state directories and secrets, installs the sshd fragment Include and login class, and reloads sshd. Upgrades never repeat system tasks.
  • Backup before overwrite: every replaced file is copied (full mode bits, including setuid) into a timestamped backup dir recorded in state.json; -rollback restores exactly the last install.
  • Sandbox profile by run class: file-only runs (check, dry-run, upgrade, rollback) execute under a full two-pass unveil with pledge reduced to file promises. System runs (first install, purge, upgrades touching the sshd fragment) skip unveil — its state is inherited by exec'd children, which would blind useradd/rcctl/sshd -t — and keep proc exec only until the system phase ends.
  • Purge honours ownership: only users recorded as created by this installer are removed; a rollback that restores an sshd fragment prints a warning to reload sshd manually instead of exec'ing under the reduced pledge.

Ticket management

filees-admin ticket create <mailbox> [--join-realm-alias <alias>] [--ttl 24h]
filees-admin ticket resend --ticket-id <ticket_uuid>
filees-admin ticket revoke --ticket-id <ticket_uuid>

A ticket is a one-time administrator grant authorising one e-mail invitation. It must be created with effective user _filees-state; creating it as root produces a private root-owned file that the set-id onboarding entry intentionally cannot read. Without --join-realm-alias it authorises creation of a new realm. With the flag, the server resolves the immutable alias immediately and stores the approved existing realm ID in ticket policy; the client never submits that ID. Revoke an unused ticket created with the wrong policy instead of editing it. The ticket file is named by sha256(canonical_email) so the file name does not reveal the address. create writes the ticket with a TTL and immediately sends its invitation; resend replaces a failed delivery capability with a fresh one without changing the ticket recipient or TTL; revoke removes it. Once its opaque invitation capability is claimed by filees-onboard take the ticket physically disappears and is replaced by an operation bundle.

Operation inspection

filees-admin operation inspect --operation-id <operation_uuid>

Displays the current state and audit trail of an onboarding operation. If an operation is in state awaiting_tunnel after the TTL has passed, the OTP is exhausted or expired, and the record can be cleaned up by filees-operation recover.

Client revocation

Revocation first writes a durable revoking record and removes the client from generated SSH/SVN runtime access. Only then does it commit the revoked client record and audit event to the service repository. An identical retry is idempotent; a different reason is rejected.

4.2 filees-operation

VerifiedClaim recovery, unfinished-operation expiry and activation cleanup are idempotent.
filees-operation recover
filees-operation inspect --operation-id <operation_uuid>

filees-operation recover scans the operations directory for claim files (.claim-*.json) and finishes them. A claim may be in two forms:

  • Claim-as-ticket — the ticket was renamed to .claim-<req_id>.json but not yet replaced by a bundle. Recovery generates the bundle and completes the final rename.
  • Claim-as-bundle — the bundle was written into the claim file but the final rename to <req_id>.json was not completed. Recovery performs only the rename.

Recovery also expires unfinished operations whose TTL elapsed, redacts their OTP and delivery address, removes expired staged keys from generated SSH/SVN access, and resumes confirmed realm-removal journals after all client credentials have been revoked. Active clients are not expired by the onboarding TTL. Recovery is idempotent and safe after an unexpected system crash. On OpenBSD it must run as the private state owner: doas -u _filees-state filees-operation recover.

4.4 Mail Outbox

VerifiedOne-shot SMTP outbox, public bootstrap composition, redaction and retry semantics.

The public SSH forced command is filees-bootstrap-entry. It atomically creates or resumes the onboarding operation and then invokes exactly one filees-mail send attempt. Authenticated control workers use the same one-shot trigger. The mail worker reads one pending invitation/activation, realm-removal OTP or data-erasure completion entry and submits it to the configured SMTP smarthost. FileES does not maintain a background mailer process.

The outbox delivery state machine:

pending  ->  sending  ->  queued    (250 after DATA; OTP and address redacted)
                      ->  pending   (4xx temporary failure; OTP preserved)
                      ->  failed    (5xx permanent failure; OTP redacted)

A stale sending entry (from a previous attempt that died without recording a result) is reclaimed with a new attempt ID before retrying. The stable Message-ID header (derived from CreatedAt, not time.Now()) makes retry safe if the smarthost accepted but the reply was lost.

To retry after a temporary failure:

doas -u _filees-state filees-mail -config /etc/filees/server.json send

Exit code 75 (ExitTempFail) means the smarthost returned a 4xx; the OTP is preserved and the command can be retried. Exit code 0 means the message was accepted (queued state). A permanent failure (5xx) sets state to failed and redacts the OTP; manual intervention is required.

4.5 Recovery

VerifiedServer claim recovery and client restart reconciliation are covered by fault injection.

Interrupted onboarding claim

doas -u _filees-state filees-operation recover

The command finishes any .claim-* file, expires unfinished operations past TTL, redacts their OTP material and removes expired activation staging. Active clients remain active. Safe to run repeatedly.

Realm removal after client revocation

A confirmed realm-removal journal is server-owned. If a crash occurs after revoke_all_clients, no client credential remains with which to resume the request. The same explicit filees-operation recover command enumerates states deleting, recovery_ready and revoke_all_clients under the repository worker lock and completes their idempotent boundaries. It is an administrative/startup action, not polling or a cyclic service.

Data-erasure retention closure

An optional data-erasure request is created only after realm-removal OTP confirmation. After active repositories, grants and client activations are removed it waits in awaiting_backup_retention. The server does not claim to purge backups automatically. Once the operator has verified the retention outcome, close it explicitly:

doas -u _filees-state filees-admin erasure complete \
  --operation-id <realm_removal_uuid>

# If policy or legal retention still requires records:
doas -u _filees-state filees-admin erasure complete \
  --operation-id <realm_removal_uuid> --partially-retained

Closure creates one final mail job. SMTP acceptance or a permanent failure scrubs the notification address. The maximum completion window shown by the client comes from repositories.data_erasure_max_days (default 90), not from GUI code.

Moving the data-repository storage root

repositories.root is an absolute, administrator-selected FSFS storage root; /var/filees/repositories is only the default. It may point to a dedicated filesystem such as /srv/filees/repositories. This is a maintenance migration, not a live configuration change: every data repository is a directory below that root, named by its repository UUID.

  1. Schedule an exclusive maintenance window. Stop all FileES client daemons that can write to this server, do not issue repository create/delete requests, and wait until there are no active svnserve -t, filees-worker or filees-client-entry processes for the installation.
  2. Verify the source before copying. Run svnadmin verify for every direct child repository; resolve any verification error before proceeding.
  3. Create a destination on the target mount that is traversable and writable only by _filees-state, then copy as root while the maintenance window remains in force. For example:
doas install -d -o _filees-state -g _filees-state -m 0750 /srv/filees
doas install -d -o _filees-state -g _filees-state -m 0700 /srv/filees/repositories

# Verify source repositories before the copy.
for repo in /var/filees/repositories/*; do
  [ -d "$repo" ] || continue
  doas -u _filees-state /usr/local/bin/svnadmin verify "$repo" || exit 1
done

# Preserve the complete FSFS directory trees, ownership and modes.
doas cp -Rp /var/filees/repositories/. /srv/filees/repositories/

# Verify the copied repositories before switching configuration.
for repo in /srv/filees/repositories/*; do
  [ -d "$repo" ] || continue
  doas -u _filees-state /usr/local/bin/svnadmin verify "$repo" || exit 1
done
  1. Change only repositories.root in /etc/filees/server.json to the new absolute path. Keep results_root and deletion_archive_root unchanged unless they are deliberately being migrated as separate state stores.
  2. Before admitting clients again, test one read-only SVN access and one controlled FileES operation. The short-lived server worker reads server.json per request, so there is no daemon to restart; the maintenance boundary is still required to prevent writes from landing in the old root during the switch.
  3. Keep the old root intact and read-only until backups and the acceptance check are complete. Rollback is simply restoring the old repositories.root value while the maintenance window is still active. Remove the old copy only under a separately approved retention policy.
Never merge two live roots or use a filesystem move while clients are connected. A repository's UUID, hooks and FSFS metadata must move together. Copy-and-verify first, then make one configuration switch; this keeps rollback available.

Client recovery after SIGKILL or power loss

The client daemon recovers automatically on the next start:

  1. Loads the full staging cache from cache.json.
  2. Runs svn cleanup and (if no missing entries) svn update.
  3. Re-classifies every cached entry by svn status; entries already marked normal (accepted by server) are dropped without re-committing.
  4. Publishes the remaining entries in bounded batches.

This idempotent reconciliation was verified in fault-injection tests (r91–r92) where a server accepted a commit but the daemon process was killed before it could update the working-copy metadata and clear the cache. The restart correctly published only the missing remaining entry.

Moved or missing working-copy root

Startup validates the root as an identity boundary before creating FileES metadata or starting a watcher. Missing .svn, a mismatched repository URL or an incompatible identity marker produces interaction_required / working_copy_missing; the daemon leaves that path untouched and runs only a lightweight recovery monitor. If the original working copy returns at the same path, the normal pipeline resumes automatically. If it was moved, use Settings Wskaż kopię: repo.locate verifies the existing root and durably rebinds the attachment without checkout. Local modifications are preserved. On Windows the active root is normally protected against out-of-band rename/delete by a non-delete-sharing directory handle, but this protection necessarily ends when FileES is stopped.

Conflict copies

Files in !kolizje/ are preserved local versions from before a server-wins conflict resolution. Each subdirectory is timestamped (YYYY.MM.DD@HH.MM_lokalne) and contains the file contents plus a .meta JSON sidecar with original path, size, and timestamp. They can be inspected and manually merged. The directory is scanner-ignored and never committed.

Orphaned passport after network loss

If the daemon loses network connectivity while holding a passport, it does not publish changes after the local TTL expires. On reconnect, the passport manager checks the actual lock on the server: if the token still matches, the heartbeat resumes; if the token has been replaced (by a force-lock or server-side expiry), the passport is marked lost. The file is returned to read-only; no automatic force-lock or commit is attempted.

Service repository projection rebuild

The clients/ subtree of the service repository is derived data. There is no general-purpose administrator command for a complete deterministic rebuild yet:

filees-admin projection rebuild   # not yet implemented

The canonical grant model is implemented despite the absence of that broad command. Activation writes the first client view in the same SVN revision as its canonical client record; an existing-realm join inherits the realm alias. Grant-authority rebuild regenerates repositories and reconciles the alias for active client views. A matching idempotent realm.alias_claim is also a bounded repair operation for older views that omitted realm_alias. Never edit a client's local cached view.json by hand: it is a server-owned projection and will be replaced by the next update.

4.7 Repository Rotation: filees-rotate

ImplementedExplicit generation change, tested end-to-end on a real FSFS repository; deliberately not scheduled — running it is an operational decision.

filees-rotate performs an explicit generation change of a hot repository: the new generation gets a new UUID and starts at r1 = a complete dump of the old HEAD (versioned properties such as svn:needs-lock included), inherits conf/ and hooks/ explicitly, and is verified (svnadmin verify plus tree comparison) before an atomic swap. The old generation becomes a frozen, commit-blocked FSFS archive with a history manifest and a meta.json recording the UUID change — the signal for client reprovisioning, since existing working copies do not survive a generation change by design.

# Evaluate triggers only (size after pack, or age of r1's svn:date):
filees-rotate -repo /srv/svn/repo -archive /srv/svn/archive -dry-run
# Rotate when a trigger fires; thresholds are configurable and validated:
filees-rotate -repo ... -archive ... -size 25GiB -age-days 365
# Bounded backup dump of the last N revisions before HEAD (never a
# second full history copy; the frozen FSFS archive is canonical):
filees-rotate -repo ... -archive ... -force -dump-depth 50

Safety contract: an flock excludes concurrent runs; repo and archive must share a filesystem (the swap is a rename); commits are blocked by a temporary pre-commit hook for the duration; rotation refuses to run while active locks (live edit passports) exist unless -break-locks is passed explicitly; every failure before the swap restores the repository as found.

When to rotate at all: for the FileES append-only profile, repository depth does not degrade performance, and FSFS binary deltas plus rep-sharing keep growth tracking unique data, not revision count. Rotation pays off only as a retention/tiering tool (SVN has no obliterate) — see the verdict in concepts/SVN_ROTATOR_CONCEPT_V2.md §7 before scheduling anything.

4.8 Realm Removal and Recovery Archives

VerifiedJournal, OTP, executor, recovery manifest, key registry, the recovery SSH transport, the GUI flow with kit generation and the data-erasure request are implemented and exercised end to end on the reference VM: multiple activations, own and foreign grants, retention 0 and >0, invariant checks (reports/REALM_REMOVAL_RECOVERY_E2E_2026-08-01.md).

Removing a FileES share is realm-scoped and irreversible for live access. It is not the same as deactivating one installation — see the table in §2.6. The design contract is concepts/REALM_DETACH_AND_ERASURE_CONCEPT.md.

Scope derivation

The worker derives the target realm from the authenticated session alone. No client payload names a realm, a repository or another installation. From the canonical service working copy the server takes a snapshot of: every active installation of that realm, every repository whose owner_realm_id is that realm (these are deleted), and every foreign repository the realm holds a grant on (the grant is withdrawn, the owner's repository is untouched). Scope derivation is fail-closed: an unreadable client projection aborts the request rather than silently narrowing it.

States

awaiting_confirmation --OTP--> deleting --> recovery_ready
                                    --> revoke_all_clients --> completed
       |
       +--> expired      (TTL elapsed, or attempts exhausted)

The OTP is peppered and stored only as a hash, compared in constant time, single-use, attempt-limited and TTL-bound. Failure to confirm leaves grants, repositories and credentials untouched. Revoking the realm's installations is deliberately the last boundary: until that point an interrupted operation can still be resumed by an authenticated client of the same realm, and a resume never widens the snapshot or produces a second dump.

Mail delivery: the confirmation OTP is queued in a durable outbox and sent by filees-mail. The trigger that drains that outbox immediately after a control-plane action runs in the parent process after proc/exec privileges are dropped, and does not attempt to re-impose a blocked unveil — fixed and regression-tested natively on OpenBSD 7.9 (previously finding B in reports/CODE_REVIEW_POST_AUDIT_r280_r318_2026-07-29.md, closed per todo-control/plan/EXECUTION_ORDER.md §1). A missing OTP mail should still be treated as a delivery problem to investigate, not silently retried indefinitely.

Recovery archives

With positive retention the removal produces one verified SVN dump per owned repository, each with a SHA-256 digest, and a manifest describing them. The manifest is capability-neutral: archive_id is an opaque UUID and is never interpreted as a filesystem path. Two independent windows apply — download_until, after which archives can no longer be fetched, and admin_grace_until, after which the receipt itself is reaped. Retention of zero means no dump is written at all, and the interface must not promise recoverable data in that case.

Access to those archives is the sole purpose of the _filees-recovery account. The client presents a per-operation Ed25519 recovery key; the separate filees-recovery-authorize helper — deliberately split from the session entry, so key lookup and session service are distinct executables — looks it up in the key registry, refuses it once download_until has passed, and emits a restricted authorized-key line whose forced command is bound to that one operation ID. The served protocol is exactly two verbs:

list <operation_id>
get  <operation_id> <archive_id>

The entry runs read-only (stdio rpath) and never sees a private key. A recovery key grants no SVN access, no shell, no re-onboarding, and no access to any other operation or repository.

Not to be confused with §4.5 Recovery, which is about recovering a damaged SVN repository on a running server. This section is about retrieving data after a realm has deliberately removed its share.

Chapter 5: Security Appendix

This appendix summarises the design invariants that were established or hardened as a result of code reviews S1–S3, the client audit, the GUI audit, and the r61–r84 review. It is written for a security-aware deployer. It does not reproduce raw review findings; it captures what was decided and why.

5.1 Core Deployment Invariants

Verified contractSecurity and ownership invariants enforced by tests and package boundaries.

I-1. Private keys never leave their origin machine. The client generates its Ed25519 installation key locally using Go’s crypto/rand. Only the public key and SHA-256 fingerprint cross the wire back to the server worker. The worker records them in the operation bundle. The server never generates, stores, or transmits private keys.

I-2. OTP never appears in arguments, environment, logs, or SVN. The OTP is transmitted through a FIFO (SSH_ASKPASS_REQUIRE=force) that is created in a private directory (0700 in \$XDG_RUNTIME_DIR), opened with O_RDONLY|O_NOFOLLOW, and zeroed after use. The OTP is stored only in the operation bundle’s pending outbox entry until the mail is accepted, at which point both the delivery address and the OTP are atomically redacted. BSD Auth receives the OTP through file descriptor 3, not through the environment.

I-3. The bootstrap Ed25519 key is a public capability, not a secret. It is compiled into the client binary and its corresponding authorized-key entry on the server can only invoke the enumeration-free filees-bootstrap-entry forced command. That entry performs one atomic onboarding take followed by at most one outbox submission. The account has DisableForwarding yes. A copy of this key does not grant any privilege beyond triggering the onboarding protocol, which still requires a valid administrator ticket.

I-4. The reverse tunnel is strictly limited. Remote TCP forwarding is allowed only to 127.0.0.1:42000. All other forwarding types (local, dynamic, stream-local, X11, agent) are explicitly prohibited. The port is statically configured to serialise infrequent deploys rather than requiring a custom listener or dynamic per-operation allocation.

I-5. The client-side helper accepts exactly one command name. The loopback SSH helper rejects global requests, non-session channels, PTY, shell, subsystem, environment, and any exec other than filees-deploy/v1. The request decoder rejects unknown fields and trailing JSON. Response size is limited to 64 KiB by io.LimitReader before decoding — not as a post-hoc check — preventing OOM from a misbehaving server worker (S3 hardening, WORKER-001).

I-6. Pledge/unveil profiles are closed in code, not configuration. No server tool accepts pledge promises or unveil paths as configuration values. Profiles are hardcoded per verb in internal/servertool/ and applied through the native sandbox wrapper. The activation worker and client entry retain only the fixed proc exec composition required for configured SVN executables; those executables must be regular and not group/other-writable. Profiles have been exercised natively on OpenBSD 7.9.

I-7. The filesystem is the transaction log. No hidden database, Unix socket, or background daemon manages state. The claim file pattern (rename ticket → .claim → bundle → committed) with fsync after each step makes crash state fully observable and recoverable with standard filesystem tools. An administrator can determine the exact recovery action by inspecting the file system.

I-8. Secret files are validated before use. readPrivateSecret rejects symlinks (Lstat + !info.Mode().IsRegular()), world- or group-writable files, empty files, files larger than 4 KiB, and files containing NUL bytes. Configuration files must be mode 0600 or 0644 (no group/other write). Paths must be absolute.

I-9. SMTP TLS errors are classified before acting on them. A transient network error during TLS handshake (TCP RST, timeout, EOF) is classified as temporary and preserves the OTP and delivery address for retry. Only certificate validation failures (unknown authority, hostname mismatch, invalid record header) are classified as permanent and trigger OTP redaction. This prevents an attacker-controlled network failure from permanently discarding the OTP (S1 hardening, SMTP-002).

5.2 Transport Hardening

VerifiedSSH command, channel, key pinning and response limits tested negatively.

T-1. Host key pinning is enforced on every client-originated SSH connection. Bootstrap and OTP tunnel connections verify the configured Ed25519 server host key before transmitting protocol data. The later possession-proof connection uses the generated installation key and the same pinned service host policy. Host-key algorithms are restricted to Ed25519.

T-2. The worker pinning is mutual and sequential. filees-worker connects to the loopback helper using the worker’s Ed25519 private key, which the helper expects. The helper’s ephemeral host key is carried in the filees.tunnel-session/v1 frame over the OTP-authenticated outer SSH session and then pinned by the worker for the reverse-forward connection. The helper binds its first valid request to one operation and client ID; a later rebind is rejected.

T-3. Client-controlled dynamic data does not shape executable command strings. The tunnel remote command is the fixed literal filees tunnel-v1, and the possession command is exactly svnserve -t. filees-entry and filees-client-entry validate SSH_ORIGINAL_COMMAND exactly. The tunnel-session frame is passed through stdin. The operation and client UUID arguments in the per-key forced command are generated server-side, validated as UUIDs and never interpreted by a shell.

T-4. BSD Auth handoff is filesystem-based, not environment-based. OpenBSD sshd does not propagate setenv values returned by a BSD Auth style to the forced command. Rather than relying on this undocumented property, FileES uses an atomic operation bundle state transition: a successful OTP verification advances the bundle from awaiting_tunnel to tunnel_authorized, which filees-entry then claims atomically as it transitions to tunnel_started. This pattern was discovered during native OpenBSD testing and results in a more auditable and robust handoff than environment passing would provide.

T-5. The worker deadline covers the entire helper session. After the TCP connection to the helper is established, the context deadline is propagated to the net.Conn using connection.SetDeadline(deadline). A context.AfterFunc callback closes the connection on cancellation even before the deadline. This prevents a misbehaving helper from keeping the worker alive indefinitely (S3 hardening, WORKER-002).

5.3 Client-Side Invariants

VerifiedDurable cache, bounded batches, lock fencing and conflict preservation.

C-1. Staging survives process death. The commit staging map is written atomically to cache.json after every received event, including during offline backoff. The daemon never loses a staged change to SIGKILL or OOM kill; recovery is idempotent.

C-2. No duplicate commits after partial success. After a crash, the restart queries SVN status for each cached entry. Entries whose paths are already in normal state (accepted by the server) are silently dropped. This was verified with fault injection at revision r91–r92 on a real SVN repository.

C-3. Local deletes are not reconstructed by update. Before each svn update (startup or poll), the daemon runs a recursive SVN status. Any missing entry defers the update to prevent SVN from reconstructing a file whose local deletion is staged but not yet committed. This defect was found during chaos testing and is now guarded by a regression test.

C-4. Conflict copies are fsynced before resolve. saveConflictCopy calls Sync() before Close(). If the fsync fails, the copy is deleted (os.Remove(dst)) and the error is propagated; svn resolve is never called with a missing or incomplete backup. This was corrected after CR-01 (high severity) in the r61–r84 review.

C-5. Passport state is always saved before early return. When Release processes multiple paths and one unlock fails, the in-memory passport map may already differ from the on-disk passports.json. A changed flag ensures that saveLocked() is called before every error return from Release. This was corrected after CR-02 (high severity).

C-6. Runtime lock recovery is PID-reuse-safe on POSIX. The lock owner file is held open with an exclusive flock. Another process trying to acquire the lock tests it with LOCK_EX|LOCK_NB: success means the original owner is dead and the OS released the flock (since flock is not inherited across exec, and the OS releases it on process death regardless of PID recycling). This replaces the earlier timestamp-based mechanism that parsed but never used the timestamp field (CR-03). On Windows the old PID-only mechanism remains; PID reuse is a known residual risk on that platform.

C-7. The GUI enforces strict import boundaries. No GUI package imports sync-engine packages (watcher, commit, client, ipcserver, errmap). The boundary is enforced by an architectural test that runs as part of go test. The daemon does not import GUI or display libraries. The sole communication channel between GUI and daemon is filees.contract/v1 over the Unix socket.

C-8. Mutation actions are gated on fresh capabilities and connection state. Lock, unlock and reservation release are offered only when the daemon reports the required capabilities and the GUI connection state is Connected (not Stale). The controller re-checks capability and connection state after native interaction, before sending IPC. Reservation release returns only an opaque row ID from the platform window; the daemon re-lists the lock and matches its token, server, repository and safe relative path before calling SVN. The daemon independently validates all paths and operation parameters; the GUI is not the security boundary.

C-9. A working-copy root is validated identity. The daemon never treats an arbitrary directory at a remembered path as the attached repository. Local .svn, the exact projected repository URL and the FileES working-copy identity marker are checked before RW or RO startup. A missing root is not recreated. repo.locate can adopt only an existing matching working copy. On Windows the active root is additionally protected against external rename/delete while the pipeline owns it.

5.4 GUI Boundary Invariants

Verified boundaryGUI cannot own daemon state, import engine packages or execute SVN directly.

G-1. Structured error information is preserved across the IPC boundary. ipcclient.ResponseError retains the full ErrorBody (code, severity, hint, message_key, details). GUI code uses errors.As to extract it and maps hint to a safe, localised user message without parsing raw text (AUD-01 correction).

G-2. A per-user lock prevents multiple GUI instances. Before initialising the tray, the composition root acquires a per-user lock (POSIX flock on Linux; named session mutex on Windows). A second instance exits before any visible effect (AUD-02 correction).

G-3. Events are cache-invalidation signals, not the sole state source. A received event triggers a repo.status fetch. The GUI never constructs its authoritative state purely by applying events. After reconnect, a sequence gap, or an unknown event, a full resync is performed.

G-4. Autostart status distinguishes current from stale. --autostart status compares the stored command with the expected command for the current executable and arguments. It returns enabled-stale if they differ, prompting the user to re-run --autostart enable from the installed path (AUD-09 correction).

G-5. Optimistic presentation never becomes lifecycle authority. After an approved repository attachment, Settings may immediately display the selected path and łączenie… while the next daemon snapshot is pending. This overlay is keyed to the durable operation ID, blocks duplicate connection, reports terminal errors, and disappears only when the authoritative ViewModel confirms attachment. It never writes repository state itself.

5.5 Identity and Grant Model

ImplementedThe realm↔client↔key map, canonical realm-to-repository grants, visibility and the desktop GUI for both are implemented and covered by Linux/OpenBSD E2E (concepts/REALM_GRANT_MODEL.md, reports/REALM_GRANTS_E2E_2026-08-01.md, reports/REALM_GRANTS_GUI_2026-08-01.md).

Realm is the precise architectural term used throughout this section, the codebase and the wire protocol. The desktop GUI shows the same concept to end users as strefa — see the GUI terminology glossary (§2.10) for the full rationale.

FileES separates three identity tiers, and access control binds to exactly one of them:

TierLifetimeRole
RealmdurableThe subject: a person or organisational unit. The only thing grants, ownership and cross-realm shares ever bind to.
Client (installation)until revokedOne machine. Transport identity: svnserve runs as --tunnel-user <client_id> forced by the server-side key entry. Per-machine audit.
Installation keyuntil rotatedEd25519 material authenticating one machine's SSH sessions. Never appears in any ACL.

The binding is created exactly once, after correct OTP authentication. For a new realm the client generates a candidate realm UUID locally and the server atomically pins it only after OTP proof. For another installation of an existing realm, an administrator instead resolves the immutable alias while issuing the invitation; the approved realm ID is stored in ticket policy and cannot be selected by the client. Administrators and users never type or copy a realm UUID into the desktop flow. Every activated record ties client_id ↔ realm_id ↔ installation key, canonically published under admin/realms/ and admin/clients/ in the service repository. A user with four machines has four client IDs and four key pairs under one realm — and the question "which keys belong to this user" always has a deterministic answer.

I-10. Grants bind to realms, never to keys or client IDs. The canonical record is (realm → repository, permissions). The svnserve authz file is a generated projection of grants onto the realm's currently active installations — reproducible at any time, never a source of truth.

I-11. Installation lifecycle never touches grants. A new installation inherits its realm's grants automatically at activation (authz regeneration); revoking one machine removes one key without affecting the realm's rights; revoking a realm removes everything in one step; key rotation is a redeploy and leaves ACLs untouched.

I-12. Administrative actions take a realm as their subject. No administrative operation accepts a public key, fingerprint or client ID as an authorisation argument (the sole exception is per-machine revocation, which targets a machine, not the subject's rights). Moving an installation between realms is not an edit — it is revoke plus fresh onboarding.

Access is granted per repository only (rw or r; a per-folder model is deliberately out of scope — every user root is its own repository, so top-level "folders" are already repositories). Repository creation is a separate server capability, can_create_repositories; rw to a shared repository never implies permission to create another repository. Ownership is derived only from owner_realm_id and alone permits further sharing. An additional global read-only client role forces r everywhere and forces repository creation off. The client learns these fields plus attachment_policy=optional|required from its server-generated view.json projection and surfaces them through IPC and the GUI. GUI values are presentation hints, the daemon independently gates local requests, and the authenticated server worker remains the sole authorisation authority. For an r repository the daemon runs an update-only pipeline: nothing is staged, passports and commits are disabled, and server-side authz remains the enforcement.

I-13. Grant authority is ownership-bound and never delegable. A client with rw may share repositories of its own realm to another realm (r or rw); access received from a foreign realm carries no right to share it onward, in any mode. Sharing requests are authorised by the server worker against the realm of the authenticated installation, never against payload claims, and the resulting grant regenerates authz and the recipients' projections without administrator involvement.
