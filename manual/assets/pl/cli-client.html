Klient CLI — przewodnik użytkownika

filees-client dla OpenBSD/amd64 i Linux/amd64 wysyła pliki do FileES na żądanie albo z crona. Wykonuje jedną operację i kończy pracę. Możesz publikować zwykły katalog bez kopii roboczej SVN; aplikacja desktopowa i dodatkowy demon nie są potrzebne.

Wersja programu: kroki poniżej wymagają CLI z poleceniami install, update, autoconfig i publish. Starsza paczka 0.1.0+r2016 ich nie zawiera. Sam numer 0.1.0 nie rozstrzyga o dostępności — sprawdź filees-client version i filees-client help.

Najkrótsza droga: zainstaluj program, użyj istniejącej aktywacji, wybierz repozytorium po nazwie i wskaż dokładny folder źródłowy. Następne wysyłki to jedno filees-client publish faktury-2026. Jeśli masz już aktywowaną instalację, pomiń krok 2.

1. Zainstaluj CLI

Potrzebujesz archiwum CLI dla swojej platformy, programów svn, svnmucc oraz ssh. Na OpenBSD zależności zapewnia pakiet subversion i systemowy OpenSSH; na Linux zainstaluj Subversion i klienta OpenSSH pakietami swojej dystrybucji. Instalator FileES nie instaluje tych zależności.

Otrzymaj paczkę z zaufanej dystrybucji. Przed uruchomieniem pierwszego programu sprawdź podpis manifestu znanym kluczem wydawcy oraz rozmiar i SHA-256 archiwum zgodnie z manifestem. Rozpakuj sprawdzone archiwum i przejdź do jego katalogu. Zawiera bin/filees-client, README i filees-client(1).

SystemInstalacja systemowa z rozpakowanej paczki
OpenBSDdoas ./bin/filees-client install
Linuxsudo ./bin/filees-client install

Program trafi do /usr/local/bin/filees-client. Instalacja bez uprawnień administratora jest również możliwa:

./bin/filees-client install --prefix "$HOME/.local"
export PATH="$HOME/.local/bin:$PATH"
filees-client version

W przykładach dalej filees-client musi być na PATH. Jeśli używasz instalacji użytkownika, zachowaj tę ścieżkę także w kolejnych sesjach i użyj jej pełnej postaci w cronie. Aktywację i publikację wykonuj jako użytkownik, który ma czytać źródło i uruchamiać harmonogram.

2. Aktywuj nową instalację

Gdy instalacja jest już aktywna w CLI lub aplikacji desktopowej, przejdź do kroku 3. Dla nowej instalacji operator serwera poda adres, plik known_hosts z przypiętym kluczem hosta oraz sposób otrzymania biletu aktywacji. W przykładach zastąp filees.example.net i adres e-mail swoimi danymi; biuro jest lokalną nazwą serwera.

Przygotuj katalog poza źródłem publikacji. Plik otrzymany od operatora zapisz jako ~/.local/share/filees/known_hosts:

install -d -m 700 "$HOME/.local/share/filees/servers"

Rozpocznij aktywację:

filees-client activate-begin \
  --server-id biuro --server filees.example.net \
  --known-hosts "$HOME/.local/share/filees/known_hosts" \
  --state-root "$HOME/.local/share/filees/servers" \
  --email user@example.net

Wynik accepted oznacza przyjęcie zgłoszenia, a nie zakończoną aktywację. Gdy otrzymasz hasło jednorazowe, uruchom następne polecenie, wpisz lub wklej hasło w osobnej linii i naciśnij Enter. Hasła nie dodawaj do argumentów polecenia.

filees-client activate-finish \
  --server-id biuro --server filees.example.net \
  --known-hosts "$HOME/.local/share/filees/known_hosts" \
  --state-root "$HOME/.local/share/filees/servers"

Sukces kończy się wynikiem active. Jeśli po wysłaniu hasła połączenie zostało przerwane, wznowienie używa zachowanej tożsamości, bez ponownego podawania hasła:

filees-client activate-resume \
  --server-id biuro --server filees.example.net \
  --known-hosts "$HOME/.local/share/filees/known_hosts" \
  --state-root "$HOME/.local/share/filees/servers"

Finish i resume korzystają z portu zapisanego podczas rozpoczęcia aktywacji. Starszy stan bez portu wymaga --remote-port PORT z wartością przydzieloną przez serwer. Zachowaj katalog aktywacji i klucz prywatny; nie umieszczaj ich w publikowanych plikach.

3. Wybierz repozytorium i wyślij pliki

Wyświetl repozytoria istniejącej aktywacji:

filees-client autoconfig

Domyślnie serwery są szukane w $XDG_DATA_HOME/filees/servers albo ~/.local/share/filees/servers. Dla innej lokalizacji dodaj --state-root /absolutna/sciezka/servers; przy kilku serwerach wybierz --server NAZWA (nazwa lub ID). Możesz też wskazać istniejący --profile /abs/client-profile.json albo --activation /abs/servers/biuro starszego CLI. Tego samego wyboru użyj przy zapisywaniu konfiguracji.

Na serwerze musi już istnieć repozytorium, do którego masz prawo zapisu. Wybierz jego dokładną, jednoznaczną nazwę. Autokonfiguracja nie tworzy repozytorium. Przykład zapisuje zadanie faktury-2026 i wskazuje rok jako źródło:

filees-client autoconfig \
  --repo 'Faktury 2026' \
  --source /home/user/published/2026 \
  --name faktury-2026

Zastąp ścieżkę swoim rzeczywistym katalogiem. Jeśli zawiera 01/, 02/ itd., miesiące znajdą się bezpośrednio w repozytorium. Wskazanie /home/user/published wysłałoby również inne lata i jego pozostałe podkatalogi. Program nie dodaje domyślnych filtrów i nie poszerza źródła do rodzica.

Sprawdź wypisane repozytorium i kanoniczne źródło. Ten krok zapisuje konfigurację, ale jeszcze nie wysyła plików. Następnie uruchom:

filees-client publish faktury-2026

Opcjonalny --message 'Faktury za październik' ustawia opis commitu, a --timeout 45m wydłuża czas operacji (domyślnie 30 minut).

Program sprawdza aktualne prawa, porównuje pliki i pokazuje postęp na stderr. Wynik published=N podaje liczbę wysłanych plików, a clean oznacza brak zmian do wysłania. Wszystkie zmienione pliki trafiają do jednego atomowego commitu. Katalog źródłowy pozostaje bez .svn.

Publikacja dodaje nowe pliki i aktualizuje zmienione. Nie pobiera zdalnych zmian, nie przenosi lokalnych usunięć do repo i nie przywraca ścieżek usuniętych na serwerze. Licznik skipped-deleted=N pokazuje te pominięcia. Polecenie publish nie przyjmuje flag przywracania ani odwrotnego uzgadniania.

Gdzie jest konfiguracja

Profil zadania, blokada i prywatny dziennik są w $XDG_CONFIG_HOME/filees-cli/NAZWA albo ~/.config/filees-cli/NAZWA. Narzędzia SVN, svnmucc i SSH są wykrywane podczas konfiguracji, a ich absolutne ścieżki zachowywane na potrzeby crona. Możesz je wybrać flagami --svn, --svnmucc i --ssh.

Powtórzenie identycznej konfiguracji jest bezpieczne. Inne źródło lub repozytorium wymaga nowej nazwy zadania. Zmiana nazwy repozytorium na serwerze zachowuje wybór jego tożsamości. Do stanu poza katalogiem domowym używaj tej samej flagi w obu poleceniach:

filees-client autoconfig --repo 'Faktury 2026' \
  --source /home/user/published/2026 --name faktury-2026 \
  --config-root /home/user/filees-jobs
filees-client publish faktury-2026 --config-root /home/user/filees-jobs

Katalog stanu musi leżeć poza źródłem. Jeśli istnieje, musi już być prywatny i zapisywalny przez użytkownika. Autokonfiguracja wykorzystuje klucz i port istniejącej aktywacji, bez ich kopiowania i bez nowego hasła jednorazowego.

4. Dodaj uruchamianie z crona

Najpierw uzyskaj poprawną publikację ręczną. Potem w crontabie tego samego użytkownika można dodać poniższy przykład. Dopasuj godziny, pełną ścieżkę programu oraz ścieżkę logu; log powinien leżeć poza źródłem.

0 9,15,20 * * * umask 077; /usr/local/bin/filees-client publish faktury-2026 --timeout 30m >> /home/user/filees-publish.log 2>&1

Własny --config-root podaj także w cronie. Dla instalacji użytkownika wskaż /home/user/.local/bin/filees-client. Cron musi korzystać z tej samej aktywacji i profilu; samo użycie innego użytkownika, np. root, nie przenosi konfiguracji. Polecenia FileES nie instalują wpisu crona automatycznie.

Jeśli pliki tworzy inny program, uruchamiaj FileES po jego sukcesie. Przykład dla ksefpuck:

/usr/local/bin/ksefpuck && /usr/local/bin/filees-client publish faktury-2026 --message ksefpuck

Zachowaj &&, aby błąd producenta zatrzymał łańcuch. Źródło powinno zawierać gotowy wynik producenta. Równoległa wysyłka tego samego zadania jest odrzucana przez blokadę; powtórny przebieg bez zmian nie tworzy kolejnego commitu.

5. Aktualizuj program

Aktualizacja używa osobnego podpisanego kanału CLI i zachowuje aktywację, profile oraz cron. Uruchamiaj ją z prawem zapisu do tego samego prefiksu co przy instalacji:

InstalacjaAktualizacja
OpenBSD, systemowadoas /usr/local/bin/filees-client update
Linux, systemowasudo /usr/local/bin/filees-client update
Użytkownika"$HOME/.local/bin/filees-client" update --prefix "$HOME/.local"

--check sprawdza dostępne wydanie bez pobierania archiwum i podmiany programu, ale nadal zapisuje stan i blokadę w prefiksie. Po przerwaniu instalacji ponów tę samą komendę; pliki są zamieniane osobno, z programem na końcu. Nie kasuj stanu instalatora, żeby wymusić starsze wydanie. Build developerski bez klucza wydawcy nie wykonuje instalacji z sieci.

Manual po instalacji czytaj przez man filees-client. W rozpakowanej paczce obu platform jest dostępny przez man -M ./share/man filees-client. Instalator umieszcza go pod prefiksem w man/man1 na OpenBSD i share/man/man1 na Linux.

Zaawansowane: kopia robocza i starszy INI

Starsze polecenia checkout i sync nadal używają pliku INI. --wc wybiera jego wpis, a nie dowolną ścieżkę. Poniżej przykład dla OpenBSD; na Linux dostosuj absolutne ścieżki narzędzi. Zastąp też tożsamość, przypięty host i URL danymi istniejącej aktywacji. URL trybu bez WC musi wskazywać korzeń repozytorium.

[tools]
svn=/usr/local/bin/svn
svnmucc=/usr/local/bin/svnmucc
ssh=/usr/bin/ssh
log_dir=/home/user/filees-log
[realm]
identity=/home/user/.local/share/filees/servers/biuro/identity/id_ed25519
known_hosts=/home/user/.local/share/filees/known_hosts
host=filees.example.net
port=22
only=!invoices
[wc "invoices"]
path=/home/user/published/2026
url=svn+ssh://_filees-data@filees.example.net/UUID_REPO

Katalog log_dir utwórz wcześniej jako prywatny, zapisywalny i poza źródłem. Dziennik zawiera czas, etap i wynik, rotuje po 5 MiB. Przykładowy INI zapisz poza źródłem, np. jako /home/user/filees-client.conf.

PrzebiegZachowanie
checkout, potem syncTworzy WC, pobiera zmiany, wysyła dodatki, modyfikacje i lokalne usunięcia. Konflikt zatrzymuje commit.
sync -nwcPublikuje zwykły katalog jak publish, bez pobierania zmian i propagowania lokalnych usunięć.
sync -nwc -restore-setJawnie pozwala ponownie dodać pliki źródła wcześniej skasowane w repo.
sync -nwc -reverse-reconcile-setPobiera jedną rewizję i doprowadza lokalny folder do jej stanu, także przez nadpisanie i usunięcie lokalnego nadmiaru. Nie commituje.
filees-client sync --config /home/user/filees-client.conf --wc invoices -nwc

Do checkout wybierz osobny, nowy katalog WC w INI. Nie używaj go jako źródła publish. Flagi restore-set i reverse-reconcile-set wymagają -nwc i wykluczają się; odwrotne zastosowanie lokalnego drzewa nie jest atomowe. Dowiązania symboliczne i nieregularne pliki wewnątrz źródła no-WC są odrzucane.

Import repozytorium i duże pliki

dump-load tworzy nowe repozytorium i nową WC z dumpa SVN. Wymaga istniejącego client-profile.json, prawa tworzenia repo oraz nowego katalogu docelowego i prywatnego stanu:

filees-client dump-load --profile /abs/client-profile.json \
  --dump /abs/archive.dump --name 'Archiwum' \
  --target /home/user/archiwum-wc --state /home/user/import-001

Rodzic katalogu stanu i celu musi istnieć. Po przerwaniu ponów dokładnie te same argumenty i stan; zachowane żądanie wznawia ten sam import. Istniejącego repo ani WC program nie nadpisuje.

Do pojedynczych dużych plików służy Whale. whale-put wysyła plik. Pobieranie zaczyna się od whale-get-quote, które podaje rozmiar i ID operacji; dopiero whale-get-confirm --id ID uruchamia transfer. whale-status, whale-retry i whale-resume używają tego samego profilu i prywatnego stanu. Pełne argumenty są w manualu poleceń.

Gdy operacja się nie powiedzie

SytuacjaCo zrobić
Nie ma polecenia autoconfig lub publishSprawdź wersję i ścieżkę uruchamianego programu. Zainstaluj sprawdzoną paczkę zawierającą te polecenia.
Nie znaleziono aktywacji albo wybór jest niejednoznacznyUżyj właściwego użytkownika, --state-root, --server, --profile lub --activation.
Repo nie jest dostępne do publikacjiSprawdź dokładną nazwę oraz prawa u operatora. Publikacja wymaga aktywnego repo do zapisu, bez obowiązkowego wypożyczenia.
Brak łączności, cofnięte prawa lub cofnięta generacjaPrzywróć łączność albo wyjaśnij stan z operatorem. CLI nie korzysta wtedy ze starej listy praw.
Zadanie już działaPoczekaj na zakończenie wcześniejszego przebiegu. Nie usuwaj blokady, żeby dopuścić drugą wysyłkę.
Zbyt niski hard limit otwartych plikówAdministrator musi zwiększyć limit dla użytkownika lub usługi. Soft limit CLI dostosowuje samo; zbyt duża partia jest odrzucana przed commit, bez cichego podziału.
Przerwane połączenie podczas commituCLI sprawdza, czy pliki znalazły się na serwerze. Po zgłoszonym błędzie przywróć połączenie i ponów to samo zadanie; niezmienione pliki nie tworzą nowego commitu.
Konflikt zwykłej WCRozstrzygnij go w SVN przed kolejnym sync. CLI nie rozstrzyga konfliktów automatycznie.

Przy Whale plik może już być na dysku, choć operacja czeka jeszcze na potwierdzenie zwolnienia serwerowego cache i rezerwacji. Sprawdź whale-status --id ID; po błędzie użyj whale-retry --id ID, a po przerwaniu procesu whale-resume --id ID, z tym samym profilem i stanem.

Kod 0 oznacza sukces; niezerowy wynik zatrzymuje łańcuch &&. Błędy operacji zwykle zwracają 1, a błędna składnia argumentów 2. Zachowuj stan aktywacji, konfigurację zadania oraz prywatny dziennik poza publikowanymi folderami.
