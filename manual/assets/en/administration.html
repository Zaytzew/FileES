Administration

This page covers the administrator's typical tasks: inviting a new person, taking an installation off the server, finishing an interrupted operation, deciding that a repository generation should change. The schemas, exit codes and state machines live in Tech Operations. Desktop clicks for the same realm live in the tray howto.

On OpenBSD run these commands as _filees-state, for example doas -u _filees-state …. Creating a ticket as root leaves a file the set-id onboarding entry cannot read.

4.1 Invite and revoke

ImplementedTicket, inspection and fail-closed client revoke exist.
filees-admin ticket create <mailbox> [--join-realm-alias <alias>] [--ttl 24h]
filees-admin ticket resend --ticket-id <ticket_uuid>
filees-admin ticket revoke --ticket-id <ticket_uuid>
filees-admin ticket list
filees-admin operation inspect --operation-id <operation_uuid>
filees-admin client revoke --client-id <client_uuid> --reason "one-line reason"
filees-admin client revoke-realm --realm-id <realm_uuid> --reason "one-line reason"
filees-admin repo transfer-owner --repo-id <repo_uuid> --realm-id <new_owner_realm_uuid>
filees-admin repo check-state [--realm-id <realm_uuid>]
filees-admin repo prune [--realm-id <realm_uuid>] [--older-than 1h] [--apply]
  • Without --join-realm-alias the invitation opens a new realm. The new desktop is asked once for an immutable alias.
  • With the flag the invitation joins an existing realm. The person joining cannot pick or rename that realm.
  • resend is for a failed first mail. It does not change the recipient or the TTL.
  • A ticket with the wrong policy is revoked, not edited.
  • client revoke takes one installation off the server. Grants and folders of the realm stay.
  • client revoke-realm takes every installation of that realm off in one call.
  • repo transfer-owner changes who owns a repository. Existing grants issued by the previous owner are left as they are.

Creating a folder, grants, public shares, load-dump and removing the FileES share are owner actions on the desktop, not extra filees-admin verbs. Exit codes, ticket file names and the fail-closed revoke sequence are in Operations. Flags and examples: filees-admin(8).

Abandoned repository creation

If an interrupted initial import leaves an extra remote folder in client projections, inspect it before changing anything. Run the commands as _filees-state:

doas -u _filees-state filees-admin repo check-state --realm-id <realm_uuid>

# dry run — changes nothing:
doas -u _filees-state filees-admin repo prune \
  --realm-id <realm_uuid> --older-than 1h

# apply only after reviewing would_remove and needs_attention:
doas -u _filees-state filees-admin repo prune \
  --realm-id <realm_uuid> --older-than 1h --apply

A candidate must report prunable:true, canonical state initializing, no staging tree, and either no FSFS or exactly r0. Active repositories, repositories at r1 or later, and ordinary deletion tombstones are not removed automatically. The tool blocks commits and checks HEAD again before making the change. After --apply, repeat repo check-state and verify the client projection.

4.2 After a crash

VerifiedRecovery is idempotent and safe to repeat.
doas -u _filees-state filees-operation recover
doas -u _filees-state filees-operation inspect --operation-id <operation_uuid>

Run recover after an unexpected stop: it finishes a half-written invitation, expires an unfinished onboarding past its TTL, and resumes a confirmed realm-removal that no client can finish anymore. Active clients are not expired. Safe to run again. How a claim file is finished is in Operations.

4.3 Where to look

Implemented

On the user's computer: Dziennik in the tray, or filees log 50. That is the structured error list for this installation.

On the server the onboarding audit is one JSON file per event under /var/filees/onboarding/audit/. The schema and event names are in Operations.

4.4 When mail does not arrive

Verified

Invitation, OTP and realm-removal mail go through the server outbox. If the first letter never arrived:

doas -u _filees-state filees-admin ticket resend --ticket-id <ticket_uuid>

If a later one-shot send failed temporarily:

doas -u _filees-state filees-mail -config /etc/filees/server.json send

Exit code 75 means try again later; the code in the letter is still valid. Exit 0 means the smarthost accepted the message. A permanent failure needs a new ticket or a check of the mail relay. The outbox state machine is in Operations.

4.5 Recover and move storage

Verified

Interrupted invitation or realm removal

Same command as §4.2: filees-operation recover. If the host was unexpectedly stopped after the realm-removal OTP was sent, once every client key was already revoked, only this command can finish the operation.

Close a data-erasure request

After a realm removal the owner may have asked for data erasure. The server does not claim to wipe backups by itself. When you have checked retention:

doas -u _filees-state filees-admin erasure complete \
  --operation-id <realm_removal_uuid>

# records must stay for policy or law:
doas -u _filees-state filees-admin erasure complete \
  --operation-id <realm_removal_uuid> --partially-retained

The window shown on the desktop comes from repositories.data_erasure_max_days (default 90).

Move the data-repository storage root

repositories.root is the administrator-chosen FSFS root; /var/filees/repositories is only the default. This is a maintenance move, not a live setting change.

  1. Exclusive window. Stop every FileES desktop that can write here. Do not create or delete repositories. Wait until there is no svnserve -t, filees-worker or filees-client-entry for this installation.
  2. Verify the source: svnadmin verify on every direct child. Fix errors first.
  3. Create a destination writable only by _filees-state, copy as root, verify the copy:
doas install -d -o _filees-state -g _filees-state -m 0750 /srv/filees
doas install -d -o _filees-state -g _filees-state -m 0700 /srv/filees/repositories

for repo in /var/filees/repositories/*; do
  [ -d "$repo" ] || continue
  doas -u _filees-state /usr/local/bin/svnadmin verify "$repo" || exit 1
done

doas cp -Rp /var/filees/repositories/. /srv/filees/repositories/

for repo in /srv/filees/repositories/*; do
  [ -d "$repo" ] || continue
  doas -u _filees-state /usr/local/bin/svnadmin verify "$repo" || exit 1
done
  1. Change only repositories.root in /etc/filees/server.json.
  2. Test one read-only SVN access and one controlled FileES action before admitting writers. There is no FileES daemon to restart; the worker reads the file per request. The window is still required so nothing lands in the old root.
  3. Keep the old root read-only until backups and the check are done. Rollback is the old path, while the window is still open.
Never merge two live roots and never move the filesystem while clients are connected. Copy and verify first, then one configuration switch.

On the user's computer after a hard stop

The desktop daemon reconciles by itself on the next start. A moved folder is Wskaż kopię, not a new checkout. Files in !kolizje/ are your local versions from a server-wins conflict — review them by hand. See troubleshooting. Claim-file shapes and projection rebuild are in Operations.

4.7 When to rotate a repository

ImplementedExplicit generation change; not scheduled.

Depth of an append-only FileES repository does not, by itself, make it slow. Rotate when you need retention or tiering — Subversion has no obliterate. Running it is a decision, not a timer. Existing working copies do not survive a generation change; every installation must attach again.

filees-rotate -repo /srv/svn/repo -archive /srv/svn/archive -dry-run
filees-rotate -repo ... -archive ... -size 25GiB -age-days 365
filees-rotate -repo ... -archive ... -force -dump-depth 50

Dry-run first. The swap, lock refusal and rollback contract are in Operations and filees-rotate(8).

4.8 Remove a FileES share

Verified

This is not deactivating one machine. It withdraws every grant of the realm, deletes the realm’s own repositories and revokes all of its installations. The desktop sequence cannot be shortened: warning, consent, notification address, directory for the .fkr kit, then the OTP. The kit is written before the irreversible step. Keep it — without it the archives cannot be fetched. The click-by-click table is in §2.6.

On a machine that no longer has FileES installed:

filees recovery download --kit FILE.fkr --output DIR

Positive retention produces one verified dump per owned repository. Retention zero writes no dump and must not promise one. States, the two time windows and the list/get recovery protocol are in Operations.

Not the same as §4.5. §4.5 is an interrupted job or a storage move on a living server. This section is fetching data after the realm chose to leave.
