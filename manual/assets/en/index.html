FileES / public manual

FileES Manual: User and Tech

FileES synchronises folders with a remote repository and lets you share files with someone who will never install the client. The manual has two parts: User covers everyday use — what to click and why, Tech covers the architecture and contracts of the system. Administration mostly uses the User part. The OpenBSD manual pages (mandoc) belong to Tech.

Languages: this is the English edition. You can also read the Polish edition. The desktop GUI speaks Polish, English, French, German and Spanish; architecture terms stay English on the wire — see the GUI terminology glossary.
Verified

Behaviour is implemented and covered by relevant native, integration, regression or chaos tests, or by a live production acceptance. A badge often carries a scope after the word — Verified on OpenBSD, Verified live, Verified cross-client — and that scope is the point: it says where the evidence comes from, not merely that some exists.

Implemented

Code exists; the description names remaining acceptance, platform or integration limits. Shipping a package does not verify every scenario.

Designed

The contract and boundaries are recorded; implementation is incomplete or intentionally deferred.

Planned

Direction is recorded, but it is not part of the current operational contract.

User

Start here if you use the desktop client or run a realm. Find instructions for everyday tasks and explanations of how each feature works. Protocol-level names stay English; the desktop speaks the language chosen in its header (in Polish a realm is a strefa).

  • Desktop howto — install the client, first folder, Settings, locks, journal.
  • Android client — QR pairing, share listing, send into mobile-uploads/.
  • Public shares — share files with someone who will never install FileES.
  • Administration — invite, revoke, recover, rotate a repository.

Tech

Start here if you deploy, maintain or audit FileES. These chapters explain the architecture, data formats and security boundaries.

  • Architecture — topology, ticket relay, OTP, SSH hop, sandbox.
  • Server install — install-server.sh, install-ssh.sh, filees-install.
  • Operations — ticket files, mail and audit schemas, rotate and realm-removal protocol, object_map, sshd and server.json.
  • Security appendix — invariants, transport, GUI boundary.
  • Man pages / CLI extract — role, invocation, flags and examples for every server command.

What is current as of 2026-10-03

Reviewed against source and signed channels on 2026-10-03. Verified applies to the named test or acceptance scope, not the whole product. Desktop has alpha and beta channels, Android its own channel, OpenBSD server alpha and beta, and Linux server a separate alpha-linux. Channels may carry different versions; stable is not published yet.

SurfaceState
Desktop daemon + trayVerified Linux and Windows; GUI is a thin IPC client
Desktop GUI languagesVerified 2026-09-11 in a real Wails window: Polish, English, French, German and Spanish, chosen from the window header or following the system; plural forms and relative times follow the chosen language without restarting the GUI
Android clientVerified live Pairing, browsing and download were accepted earlier; on 2026-09-27 the owner confirmed the new upload indicators and completion of a large queue after correcting server temporary storage. Phone-specific background limits remain. See Android.
Activation and realm joinVerified The client generates its key locally, supplies OTP through embedded SSH with host-key pinning, and resumes an accepted attempt.
Selective attach, locate, detach, load-dumpVerified
Realm grants and visibilityVerified owner-only; no transitive re-delegation
Repository editing policyVerified live 6/6 on two Windows clients
Public SharesVerified live HTTPS endpoint, OTP, branding, ZIP; each fresh visit freezes one revision and lists the shared folder as it stands at that revision
FILEES-BIN / filees-installVerified on OpenBSD Installation and updates from a signed channel. The manifest includes programs, man pages and integration files. The installer bounds rollback history and cleans staging. Interruption acceptance for each new update path remains separate.
Windows MSI / self-updateImplemented MSI installs the daemon/GUI pair and a native startup supervisor. Stopping the old supervisor and replacing programs have regression coverage. Full acceptance of a legacy upgrade, repair and interrupted uninstall remains necessary.
Linux serverVerified in the laboratory Installer, PAM, systemd/cron scheduling and updater; acceptance on Debian 13 and Fedora 44. A signed alpha-linux channel exists. Fedora receives an SELinux policy; Linux does not provide the OpenBSD pledge/unveil contract. See installation.
Upload Channel — sender sideVerified 2026-09-12 on a production host: public upload, antivirus scan and commit into the delivery repository. It needed three fixes to package defaults first; the installer still does not schedule the upload-reap job, and without it uploads are accepted and never processed (see Install). slots/DROPPER remain deliberately off
Upload Channel — recipient sideImplemented and shipped Shelf listing, read-only fetch on demand and placement in the parent folder without replacement. Real sparse download was tested on Windows; this does not replace manual acceptance of every GUI action.
Daemon memory safetyImplemented Bounded IPC frames and controlled shutdown under memory pressure. An initial measurement exists; long-term observation is a separate weekly task. There is no proof ruling out a memory leak yet.
Server capacity alertsImplemented GUI and email notifications passed live acceptance. The newer write gate and session barrier still need full OpenBSD, interruption and disk-full acceptance. See configuration.
Encryption, Backstage, user administration consolePlanned Crypto has an isolated prototype; it does not protect officially released repositories. Backstage and the console remain concepts.

On the server: filesystem first, no resident FileES daemon, system sshd as the only privileged endpoint. The desktop client is the opposite shape — a resident per-user daemon with a thin tray GUI — and the two should not be confused.
