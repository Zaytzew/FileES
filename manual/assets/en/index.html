FileES / public manual

FileES Manual: User and Tech

FileES synchronises folders with a remote repository and lets you share files with someone who will never install the client. This HTML set is the public manual for the system, split into two parts: User covers everyday use — what to click and why, Tech covers the architecture and contracts of the system. Administration mostly uses the User part. The OpenBSD manual pages (mandoc) belong to Tech.

Version 0.1.16 Date 2026-09-14 Server OpenBSD 7.9 · signed release channel Client Linux and Windows desktop · Android GUI PL · EN · FR · DE · ES
Languages: this is the English edition. The Polish edition is under assets/pl/. The desktop GUI speaks Polish, English, French, German and Spanish; architecture terms stay English on the wire — see the GUI terminology glossary.
Verified

Behaviour is implemented and covered by relevant native, integration, regression or chaos tests, or by a live production acceptance. A badge often carries a scope after the word — Verified on OpenBSD, Verified live, Verified cross-client — and that scope is the point: it says where the evidence comes from, not merely that some exists.

Implemented

Code exists, but some target-platform packaging or later integration remains incomplete.

Designed

The contract and boundaries are approved; implementation is incomplete or intentionally deferred. No section currently carries this level — it is kept because the distinction is real, not because something is marked with it.

Planned

Direction is recorded, but it is not part of the current operational contract.

The previous single-file manual-filees.html is a stub. Each page keeps the filees:space visual system and has no network dependencies. FileES is a work-in-progress. A maturity badge is not a product release.

User

Start here if you use the desktop client or run a realm. The tone is: what to click, what happens, why the feature exists. Protocol-level names stay English; the desktop speaks the language chosen in its header (in Polish a realm is a strefa).

  • Desktop howto — install the client, first folder, Settings, locks, journal.
  • Android client — QR pairing, share listing, send into mobile-uploads/.
  • Public shares — share files with someone who will never install FileES.
  • Administration — invite, revoke, recover, rotate a repository.

Tech

Start here if you implement, audit or deploy. The tone is contracts, rejected alternatives and what must stay true.

  • Architecture — topology, ticket relay, OTP, SSH hop, sandbox.
  • Server install — install-server.sh, install-ssh.sh, filees-install.
  • Operations — ticket files, mail and audit schemas, rotate and realm-removal protocol, object_map, sshd and server.json.
  • Security appendix — invariants, transport, GUI boundary.
  • Man pages / CLI extract — role, invocation, flags and examples for every server command.

FILEES-BIN / filees-installVerified on production OpenBSD: hosts install and upgrade from the signed channel alpha; the latest recorded upgrade, 2026-09-13, carried the upload shelf server release
Windows MSI / self-updateImplemented one MSI installs the daemon, the GUI and the start scripts together; signed self-update of the pair was accepted on earlier releases. The MSI carries no Authenticode signature, and an MSI upgrade over an installed pair has not been exercised
Linux serverImplemented the server code builds and its test suite runs on Linux — first measured natively on Debian 13, 2026-09-09, after which the only failures left were defects that had nothing to do with the platform. Installation, service supervision, privilege drop and packaging are not implemented yet: there is no Linux installer, and pledge/unveil confinement does not exist outside OpenBSD, so on Linux that is the administrator’s job
Upload Channel — sender sideVerified 2026-09-12 on a production host: public upload, antivirus scan and commit into the delivery repository. It needed three fixes to package defaults first; the installer still does not schedule the upload-reap job, and without it uploads are accepted and never processed (see Install). slots/DROPPER remain deliberately off
Upload Channel — recipient sideImplemented an upload shelf appears under its parent repository, lists what arrived, fetches chosen files on demand and read-only into a new folder you name, and places a file into the parent working copy without overwriting anything. Tested including a real sparse fetch on Windows; not yet accepted by hand in a released GUI, and not yet shipped in a desktop release
Daemon memory safetyImplemented IPC frames are read with small initial buffers and bounded time; under sustained memory pressure the daemon stops taking new work, saves its queue and asks to be restarted instead of being killed. No long-run observation of this code has been completed yet

On the server: filesystem first, no resident FileES daemon, system sshd as the only privileged endpoint. The desktop client is the opposite shape — a resident per-user daemon with a thin tray GUI — and the two should not be confused.
