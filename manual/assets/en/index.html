Protocols, ticket relay, pledge/unveil, requirements, mandoc, how this origin is published.

The previous single-file manual-filees.html is a stub. Each page keeps the filees:space visual system and has no network dependencies. FileES is a work-in-progress. A maturity badge is not a product release.

User

Start here if you sit at a desk or run a realm. The tone is: what to click, what happens, why FileES bothers. Wire names stay English; the desktop speaks everyday Polish (strefa is a realm).

  • Desktop howto — install the client, first folder, Settings, locks, journal.
  • Public shares — hand a packet to someone who will never install FileES.
  • Administration — invite, revoke, recover, rotate. Still a user, with more keys.

Tech

Start here if you implement, audit or deploy. The tone is contracts, rejected alternatives and what must stay true.

  • Architecture — topology, ticket relay, OTP, SSH hop, sandbox.
  • Server install — install-server.sh, install-ssh.sh, filees-install.
  • Operations — ticket files, mail and audit schemas, rotate and realm-removal protocol, object_map, sshd and server.json.
  • Security appendix — invariants, transport, GUI boundary.
  • Man pages / CLI extract — role, invocation, flags and examples for every server command.
  • Publishing this set — ^/manual is the document root; svn up is the publish step.

Publishing this set on manual.filees.space

Public Shares and the HTML manual share one HTTPS origin. httpd does not know realms or slugs. It only owns a small static allowlist; everything else is FastCGI. A chapter file left next to index.html as /architecture.html would therefore be treated as a virtual FileES path and return the branded 404.

This directory is the document-root image. It lives in Subversion as ^/manual. On the host, /var/www/htdocs is a working copy of that subtree. svn update is the publish step. Do not add a new location and do not reload httpd.
