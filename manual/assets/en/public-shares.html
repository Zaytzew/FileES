Public shares

Share files with someone who will never install FileES. This is not a second way to write into your folders. Trust zones, the object map and the OTP protocol are in Tech Operations.

5.1 What this is

Verified live

A public share is a read-only landing page at the same HTTPS address as this manual. The visitor never receives write credentials. An upload shelf works in the opposite direction — receiving files from someone outside (§5.7) — and does not share this process or these secrets with a public share.

The page uses no JavaScript, no cookies and no third-party resources. Branding is the filees:space system plus the owner logo and accent already stored on the server.

Why the public process never talks to Subversion itself is in Operations.

5.2 The share address

The public address is always:

https://<server-domain>/<realm-alias>/<slug>

Unknown, revoked and deleted addresses share one branded HTTP 404 that does not echo the path or the reason. The allowlist that also serves this manual is in Operations, canonical share address and Operations, htdocs tree.

5.3 Not a live mirror

VerifiedImplemented contract, not a defect.

A channel with no frozen revision follows HEAD, but not live: every new visit to the canonical address re-derives the file listing from the current SVN tree, so a file added later appears, a removed one disappears, and a rename shows under its new name. What is not live is an already-issued visit — a link carrying a ?v=… token freezes to whatever HEAD was at that visit, and does not catch up with later changes even to the same file. A channel with an explicit, positive revision freezes every visit to that one snapshot permanently, regardless of HEAD.

An empty folder is a legal placeholder. That is why the desktop copy says the share is not a live mirror of the folder — that describes a visit, not a channel following HEAD. The two clocks (object_map versus revision) are in Operations.

5.4 Open or closed

Open channel. Anyone with the address. You may set a shared password. After the password the visitor gets a twelve-hour signed link. The password screen shows your mark; it does not show the alias or the slug.

Closed channel. Each recipient gets their own invitation in the URL. The link alone is not enough. They ask for a code, receive an eight-digit OTP by mail, type it on the same page, then get a signed link that lasts until that code expires. Copying the signed link during that window carries the remaining access. After expiry the invitation URL returns to the gate. After revoke it is 404.

The public page never shows e-mail addresses. How hashes, epochs and visit tokens work is in Operations.

5.5 From the desktop

Udostępnienia publiczne appears only for the canonical owner, and only when the daemon advertises the complete list / create / update / revoke / delete set. Create and edit need an attached working copy.

  • Pick the working-copy root or any folder under it.
  • At most 4096 regular files. .svn and .filees are skipped. Symlinks are rejected.
  • Revoke stops delivery and keeps the record. Delete keeps an address tombstone.
  • A recipient list makes a closed channel. An empty list makes an open channel, optionally with a password. The password is never stored in the clear.
  • Empty revision follows the latest. A positive revision freezes that snapshot.

After opening the share, the visitor sees a collapsed-by-default details tree: name, type icon, size, download. They may take one file, one folder or the whole share as a ZIP. That bundle has its own limit, separate from the share: 512 files by default, configurable up to 4096. A share may legally hold more objects than one bundle may carry, and a request over the limit is refused rather than truncated. This version has no thumbnails.

5.6 Turning it on

Public shares are installed disabled. After you have edited server.json and public-links.json, start authority before links, then reload httpd. The exact commands, health rule and man pages are in Operations.

5.7 Upload shelves: receiving files

Verified liveSender side on a production host, 2026-09-12: upload, antivirus scan, delivery into the shelf. Taking the files on the desktop is implemented and not yet accepted by hand (§2.6).

A public share gives files out; an upload shelf takes them in. A shelf is always closed: there is no anonymous upload and no public form that anyone could find.

Creating a shelf. In the actions of the repository the files should arrive into, choose Upload shelves. You give the address suffix (3–64 lowercase letters, digits or single hyphens) and the contributors’ e-mail addresses — at least one. You also decide whether a contributor has to enter a one-time code sent by e-mail before uploading.

What the contributor gets. Each address receives its own invitation link:

https://<server-domain>/<realm-alias>/<slug>?invite=…

The invitation is personal and opaque; it does not contain the e-mail address. Without it, or with a wrong one, the address answers with the same 404 as any unknown page. If you asked for the e-mail code, the page first asks for the address and sends the code, and the file field appears only after the code. The contributor then drops a file or clicks to choose one and presses Wyślij; the page asks them to keep the tab open until the server confirms receipt. In this version the upload page is in Polish only.

What happens to the file. The public process only puts the file into an intake queue and never talks to Subversion. A separate job on the server scans it with the antivirus program, then commits it into the shelf repository — or, if the scan rejects it, records it in Quarantine, where it can be reviewed for 48 hours. A file that cannot be scanned is held back, never delivered unscanned. The server limits the size of one file (max_upload_size, 1 GiB in the example configuration).

Revoke and delete. Revoking stops the address accepting files; the address stays reserved and what has arrived stays with you. Deleting removes the shelf’s policy, reserves the address for good and does not delete the received files.

Named places per contributor (slots) and the DROPPER release preflight exist in the design and are deliberately switched off. Upload shelves need the server side turned on and a scheduled intake job; that is the administrator’s part, in Install.
